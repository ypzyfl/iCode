# 桌面端集成登录方案（iCode × AIxCoding Desktop）

> 分支：`lhc/aixcoding_login`（iCode 侧）/ `fix-1008`（桌面端侧，只读参考）
> 更新日期：2026-10-08
> 配套文档：[桌面端集成登录开发计划.md](桌面端集成登录开发计划.md)、[TUI登录改造方案.md](TUI登录改造方案.md)（独立 TUI 登录的底层设计）

---

## 1. 背景与两个场景

iCode 的登录能力要同时服务两个互不干扰的场景：

| 场景 | 形态 | 登录方式 | token 消费方 |
|---|---|---|---|
| **S1 独立 TUI** | 用户自己开终端跑 `icode` | iCode 自己的设备码登录（`/login`） | 同事通过 `get_login_session().stored_token` 取 token 访问 LLM |
| **S2 桌面端集成** | AIxCoding 桌面端（Electron）选择 iCode 引擎后，以 ACP 子进程拉起 `chrys acp` | **桌面端登录**，iCode 免二次登录 | 同一个 `get_login_session()` API |

S2 的硬约束：**不得影响 S1**——没有桌面端环境变量的进程，行为与改造前完全一致。

## 2. 现状盘点（集成面两侧的事实）

### 2.1 桌面端（agent_studio_new @ fix-1008）

- 桌面端主进程跑设备码登录（`apps/desktop/src/main/device-code-auth-service.ts`），拿到 `token`（既当账户凭证又当模型凭证，即 `modelCredential`），safeStorage 加密落盘，**无 refresh 流程**，业务 401 即强制重登。
- 引擎选择：`DesktopAgentEngineSchema = z.enum(['pi','icode'])`（`packages/contracts/src/desktop-agent-engine.ts`），设置弹窗里选；每个会话按 ACP over stdio 拉起一次引擎子进程（`StdioAcpConnectionFactory`）。
- **拉起 icode 子进程时已经注入的环境变量**（`apps/desktop/src/main/runtime-composition.ts` 约 2110–2164 行）：
  - `OPENAI_API_KEY = <登录 token>` —— `modelCredential` 按提供方映射的变量名（`desktop-agent-connection-service.ts` 的 `AGENT_CONNECTION_ENVIRONMENT_BY_PROVIDER`），**模型调用链路今天就靠它工作**；
  - `AIXCODING_USER_EHR = <用户 EHR>`（`userContextEnvironment`）；
  - `HOME` / `APPDATA = <账户私有 chrys-home>` —— icode 的配置根被隔离到账户目录；
  - `CHRYS_MODEL_PROFILE`、`PYAPP_INSTALL_DIR_CHRYS`。
- 桌面端替 icode 写好的配置（模型/agent profile YAML）**不含任何凭证**（`api_key: ''`），凭证只走环境变量。
- 桌面端**不提供**：token 下发本地 HTTP/IPC 代理、token 刷新、子进程内 token 热更新（换登录 = 新 epoch = 重新拉子进程）。

### 2.2 iCode（本仓库 @ lhc/aixcoding_login）

- 登录实现全部在 `aixcoding/` 包（见 [项目索引.md](项目索引.md) §5）；`src/chrys` 只有约 108 行接线。
- 登录态唯一权威入口：`aixcoding.auth.get_login_session()`（进程单例）：
  - `session.stored_token` → 本地判定（store 里凭据存在、未过期、token 非空）；
  - `await session.check_silent()` → `user/info` 网络校验（服务端拒绝→清凭据；网络故障→保留，"离线不是登出"）；
  - `session.logout()` → 清 store。
- token 目前**仅身份展示**，未注入 LLM 请求（设计上 `stored_token` 就是留给下游的交接点）。
- ACP 路径（`chrys acp`）**没有任何登录门槛**；headless 同样无门槛。

### 2.3 结论：缺的那一环

S2 里桌面端已经把 token 送进了子进程环境，但 iCode 的登录层（`LoginSession`）只认自己的 `CredentialStore`。同事在 S2 下调 `stored_token` 会拿到 `None`，"已登录"状态对下游不可见。需要一层**委托登录（delegated credential）**：从环境变量识别父进程（桌面端）下发的 token，让它流经同一个 `LoginSession` API。

## 3. 总体设计

**原则：父进程拥有会话，子进程只继承，不拥有。**

```
桌面端（设备码登录，safeStorage 落盘，拥有生命周期）
   │  spawn: chrys acp --agent <profile> ...
   │  env: CHRYS_AUTH_DELEGATED_TOKEN=…（主通道）
   │       AIXCODING_USER_EHR=…, OPENAI_API_KEY=…（兼容通道/模型凭证）
   ▼
iCode 子进程
   LoginSession.__init__ → detect_delegation()   # 冻结后的进程 env，读一次
   stored_token   → 委托 token（遮蔽本地 store，只读、不落盘）
   check_silent() → 用委托 token 调 user/info 校验；被拒 → 只取消遮蔽，不销毁任何东西
   logout()       → 委托态下 no-op（会话归桌面端管）
```

四条设计决定及理由：

1. **RAM-only，不落盘。** 委托 token 只存在于进程内存。桌面端重登/过期后重拉的子进程天然拿到新值；把它写进 `chrys-home` 的 store 反而会留下桌面端已登出后的僵尸凭据。
2. **只读。** 子进程不能 revoke 父进程的会话（服务端也不支持），所以 `logout()` 在委托态下必须是 no-op；服务端拒绝委托 token 时只置 `_delegated_rejected` 标志，**绝不动本地 store**。
3. **遮蔽而非合并。** 委托 token 优先于本地 store（`stored_token` 先查委托）。被服务端拒绝后取消遮蔽、回落 store——这保证"桌面端 token 失效"不会把用户自己 `/login` 存的凭据一起埋葬，也不会出现"明明存了凭据却永远读不到"的死锁。
4. **同一 API 出口。** 下游（同事的 LLM 网关取 token、未来的请求头注入）继续只认 `get_login_session()`，S1/S2 对下游透明。

## 4. 环境变量契约

检测顺序（`aixcoding/auth/delegation.py::detect_delegation`，读 `bootstrap_runtime` 冻结后的进程 env，会话构造时读一次）：

| 优先级 | 变量 | 语义 |
|---|---|---|
| 1（主通道） | `CHRYS_AUTH_DELEGATED_TOKEN` | 父进程（桌面端）的账户 token，**出现即委托**。值做 strip，空串视为未设置 |
| 1a | `CHRYS_AUTH_DELEGATED_EHR`（可选） | 身份提示，首个 `user/info` 往返前可展示 |
| 1b | `CHRYS_AUTH_DELEGATED_NAME`（可选） | 显示名提示 |
| 2（兼容通道） | `AIXCODING_USER_EHR` **且** `OPENAI_API_KEY` | 桌面端 ≤ fix-1008 的行为：模型凭证就是登录 token，且总是伴随用户 EHR 注入。两者都非空且主通道未设置时，按委托接受，`source` 标记为 `OPENAI_API_KEY` |

兼容通道的风险与边界：独立 shell 里恰好同时导出这两个变量（例如用户手工导出 EHR + 真实 OpenAI key）会误判为委托。后果可控：`check_silent()` 会拿这个 token 去打 `user/info`，服务端拒绝（`用户不存在`）→ 委托被取消遮蔽 → 回落本地 store，最终表现仍是"未登录"，与不设这两个变量时一致；期间无任何本地状态被破坏。主通道落地后桌面端不再依赖该启发式。

**桌面端可选加固（一行改动，非必须、非阻塞）**：在 `runtime-composition.ts` 的 icode 连接 environment 块里加 `CHRYS_AUTH_DELEGATED_TOKEN: <modelCredential>`（与 `OPENAI_API_KEY` 同值同生命周期），可选同时给 `CHRYS_AUTH_DELEGATED_EHR`/`CHRYS_AUTH_DELEGATED_NAME`。**不加也完全可用**——现有 fix-1008 构建靠兼容通道即可工作；加它的动机是：① `OPENAI_API_KEY` 语义上是"模型凭证"变量，桌面端今天恰好让账户 token 与它同值，将来两者一旦分离（或按提供方换成 `ANTHROPIC_API_KEY` 等其他变量名，兼容通道就认不出了），复用会静默失效，而专用变量是稳定契约；② 消除独立 shell 的误判窗口；③ 让两端的集成契约显式、可版本化、桌面端侧可测。

## 5. `LoginSession` 语义（改造后）

| 入口 | 无委托（S1，行为不变） | 委托生效（S2） | 委托被服务端拒绝后 |
|---|---|---|---|
| `delegated_credential` | `None` | `DelegatedCredential(token, ehr, display_name, source)` | `None` |
| `stored_token` | 读 store | **委托 token**（遮蔽 store） | 回落读 store |
| `check_silent()` | user/info 校验 store 凭据；拒绝→清 store | user/info 校验委托 token；**拒绝→仅置 rejected 标志**；网络故障→None 且保留 | 走"无委托"列 |
| `logout()` | 清 store | **no-op**（会话归桌面端） | 清 store（恢复正常语义） |
| `complete_login()` | 设备码流程 + 落盘 | 允许（落盘但被遮蔽）；TUI 侧已由托管提示拦住，实际不可达 | 同"无委托" |
| `request_device_code()` | 不变 | 不变 | 不变 |

新增构造参数 `delegated: DelegatedCredential | None = None`：`None`（默认）= 从环境自动检测；测试可显式注入。进程单例 `get_login_session()` 的共享语义不变（MemoryBackend 降级时凭据在实例内，仍必须共享同一会话）。

## 6. 各前端形态的行为

| 形态 | 行为 |
|---|---|
| **ACP 子进程（桌面端，S2 主形态）** | 无登录门槛（原本就没有）；`get_login_session()` 自动检测委托 → 下游 `stored_token` 拿到桌面端 token；启动静默检查（`app.py` 的 `_silent_login_check`）照常跑，对委托 token 做 `user/info` 校验，异常全部吞掉 |
| **独立 TUI（S1）** | 环境里没有委托变量 → 检测结果 `None` → 全链路与改造前逐字节一致 |
| **TUI 但带委托 env**（边缘：在桌面端注入过的环境里手工起 TUI） | `/login` 不弹设备码对话框，toast「登录由桌面端统一管理」；`/logout` toast「退出登录由桌面端统一管理」，不清任何东西。新增 msg：`tui.login.managed_by_desktop` / `tui.login.logout_managed_by_desktop` |
| **headless `icode run`** | 与 TUI 同理：无 env 不变；有 env 则 `stored_token` 返回委托 token |

## 7. 安全考量

- 委托 token **只进内存**：不写 `CredentialStore`，不进日志/traces（沿既有约定，token 不出现在任何持久化产物里）。
- 子进程 env 本就是桌面端的既定凭证通道（`OPENAI_API_KEY` 同样如此）；方案没有扩大暴露面，只是让登录层"认得"它。
- 桌面端侧 token 从不进 renderer（ADR 0013），本方案不改变这一点。
- 隔离的 `HOME`/`APPDATA` 使 S2 的 icode 配置根与独立 TUI 的 `~/.chrys` 物理分离，两个场景的本地凭据互不可见——"不影响独立 TUI"由此再加一层保险。
- 兼容通道要求 EHR + 模型 key 成对出现，降低误判；主通道变量名带 `CHRYS_AUTH_` 前缀，与既有 `CHRYS_AUTH_ENVIRONMENT` 家族一致。

## 8. 边界情况

| 情况 | 行为 |
|---|---|
| 桌面端登出/过期后子进程仍在跑 | 委托 token 在本进程内不会变；`user/info` 拒绝后取消遮蔽、`stored_token` 回落 store（通常为空 → 表现为未登录）。桌面端 401 强制重登后重拉的会话拿新 token |
| 内网不可达（离线） | `check_silent()` 网络错误 → `None` 但委托保留（"离线不是登出"对两种凭据一视同仁） |
| 环境 tier 不匹配（如 `CHRYS_AUTH_ENVIRONMENT=local` 却收到 prod token） | `user/info` 打到 local 端点必然拒绝 → 委托取消遮蔽，回落 store。桌面端不设置该变量（默认 prod），正常不触发 |
| 委托 + 本地凭据并存 | 委托优先；委托被拒后本地凭据顶上；`logout()` 在委托生效期是 no-op（本地凭据也不清——语义是"这个会话归桌面端管"） |
| 环境变量晚于进程启动才被设置 | 检测在会话构造时一次性完成（env 已被 bootstrap 冻结），不受后续 `os.environ` 写入影响——与 `CHRYS_AUTH_ENVIRONMENT` 的既有语义一致 |

## 9. 不变式（评审清单）

1. 全部新代码在 `aixcoding/`；`src/chrys` 只增接线（本次仅 `screen.py` 托管提示分支 + 2 个 msg）。
2. 不新增 Settings 字段；环境切换/委托检测都是纯环境变量。
3. `get_login_session()` 仍是进程单例，所有调用方共享。
4. 无委托时（S1）：`stored_token`/`check_silent`/`logout`/`complete_login` 行为与改造前完全一致（既有测试零改动通过）。
5. 服务端拒绝只清"自己拥有的"凭据；网络故障永不清凭据。
6. i18n：`aixcoding/` 内文案不进 catalog；`src/chrys` 的新 toast 走 `msg()` + zh-Hans 翻译 + oracle 登记（count 2227→2229）。
7. ACP/headless 路径零登录门槛的现状保持。
