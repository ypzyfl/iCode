# 模型排队桌面端透传说明

> 面向：桌面端（agent_studio_new）开发联调、iCode 排队功能的排查与验收。
> 现行口径：`model-queue-progress` design v1.4（2026-11-25 签认，D1 带 / D2 加 / D3 补）。
> 关联文档：本目录 `requirements.md`（总口径）、`intranet-verification.md`（内网步骤）、
> `../batches/model-queue-progress/design.md`（实现设计与签认）。

## 1. 一句话结论

iCode 在网关排队期间通过 ACP 扩展通知 **`_chrys/queue_status`** 把排队位置透传给桌面端；
桌面端已实现消费并渲染排队横幅（含取消按钮）。v1.4 起载荷为**四字段**，新增 `requestId`
（该次请求的 `Chrys-Request-Attempt-Id`），桌面端按请求粒度同步改造。

## 2. 链路全景

```
网关（FIFO 队列）
  │ SSE event:queue_status {position, queueSize}（约 20s 心跳）
  ▼
iCode wire 层 guard_queue_frames（定制包，吸收帧、续活看门狗）
  │ QueueStatusTracker.observing 转发时回填 request_id          ← v1.4
  ▼
WireCallObserver.on_queue_status → EventBus GatewayQueueStatus（session 级事件）
  │ TUI WaitingRow 文案 / CLI 追加行（均不读 request_id）
  ▼
ACP server.py 挂点 → ext_notification("chrys/queue_status", payload)
  │ Python ACP SDK 发送时自动加 "_" 前缀（acp/agent/connection.py:206）
  ▼
线上方法名 = _chrys/queue_status
  ▼
桌面端 chrys-protocol.ts:63 注册 → #handleModelQueueStatus 校验载荷
  → bindPrompt 绑定会话 → model-queue service（source='engine'）
  → 渲染层排队横幅（ConversationPane.vue，与 Pi 代理路径共用同一 UI）
```

要点：

- **方法名的 `_` 前缀不是拼写差异**：iCode 代码写 `chrys/queue_status`，SDK 在 JSON-RPC 发送层
  自动加 `_`（扩展方法约定）；桌面端注册的就是 `_chrys/queue_status`，两端一致，无需任何一端改名。
- `sessionId` 是路由键（`session/new` 返回给桌面端的会话 id），桌面端靠它把通知绑到当前 prompt；
  缺失该键整条通知会被桌面端丢弃——**不能**用 `requestId` 取代。

## 3. 载荷契约（v1.4 四字段）

| 通知 | 载荷 | 时机 |
|---|---|---|
| 排队中 | `{"sessionId": str, "requestId": str, "position": int ≥ 0, "queueSize": int}` | 每个 (requestId, position) 首次出现 |
| 放行 | `{"sessionId": str, "requestId": str, "released": true}` | 排队后首个数据帧到达，一次（D1：带 requestId） |

字段语义：

- **sessionId**：会话 id，值与语义不变；桌面端横幅路由键。
- **requestId**：应答该次请求的 HTTP 尝试所带的 `Chrys-Request-Attempt-Id` 请求头值（32 位小写 hex）
  = 网关队列元素键 = iCode 调 cancel 接口时 body 里的 `request_id`。**每个 HTTP 尝试一个新值**：
  SDK 重试/重定向、wire 重试、整轮重试各算一个；一个 turn 内多次模型调用会出现多个。
- **requestId 可能缺席**（键被省略，不是空串/null）：tracker 未武装时（应答尝试没有该请求头、
  或 base_url 无法推导 cancel 地址；产品路径不会发生）。桌面端必须按可选字段处理。
- **去重**（D2：键含 requestId）：同一 (requestId, position) 只发一次（网关心跳重复同名次被吞）；
  重试产生新 requestId，即便同名次也重发——保证桌面端手上的 id 永远是活请求的。
  `chrys/turn_started` 重置去重（中断后下一轮不被残留值吞帧）。
- 桌面端不应依赖 JSON 键序。

## 4. 版本配套矩阵

| 组合 | 行为 |
|---|---|
| 新 iCode（v1.4）+ 现版桌面端 | 多出的 `requestId` 被忽略，横幅照常（现版处理器只读已知键） |
| 新 iCode（v1.4）+ 改造后桌面端 | 按请求粒度消费 `requestId`（桌面端同步改造，非本仓范围） |
| 旧 iCode + 改造后桌面端 | 载荷无 `requestId` → 桌面端须回退按 `sessionId` 展示（可选字段） |

## 5. 桌面端展示口径（现状，2026-11-24 实核）

桌面端横幅文案与 iCode 自有前端口径不同（桌面侧责任，iCode 不改）：

| 项 | 桌面端行为 | 与 iCode 口径差异 |
|---|---|---|
| position ≥ 1 | 「当前模型请求量大，请求排队约 N 人…」，N 取 **queueSize**（队列总长） | iCode TUI/CLI 用 position（前方人数） |
| position = 0 | 「正在获取模型资源…」 | iCode v1.2 已定性 position 0 ≠ 已获资源（队首仍可 QUEUE_TIMEOUT），桌面文案偏乐观 |
| 排队超时/队满 | **不走排队横幅**（rejected 横幅仅 Pi 代理路径可达；engine 通知只有 queued/released 两相） | iCode 的 QUEUE_TIMEOUT 表现为普通 turn 失败报错 |
| 「取消排队」按钮 | 现版为 Pi 代理专用（依赖代理注册的取消详情，engine 路径返回 not_found） | iCode 的网关取消走「停止」按钮（session/cancel → iCode 补发 cancel，v1.1 实现）；桌面端改造后可用 requestId 自行调 cancel 接口 |
| 放行 | released 通知到达，横幅消失，随后开始流式出字 | 一致 |

## 6. 联调步骤

前提：桌面端只运行 `applicationConfig.icode.binaries` 固定的 iCode 构建——**须指向含排队功能的本分支构建**，
否则横幅不会出现。

1. **本地模拟**（无网关）：`mock_server/model_concurrency_verify/`（仓外未跟踪资产）起 mock 网关，
   `-m QueueMock` 模式下发排队帧；iCode 侧用 TUI/CLI 先自查三端文案（见 `intranet-verification.md` §2–3）。
2. **桌面端连通**：桌面指向上述构建 + mock/内网网关，发起会占到并发槽位的请求。
3. **观察通知**（桌面主进程日志 `[model-queue] event queued <appSessionId> <position>`，或抓 ACP stdio）：
   - 排队中 `{"sessionId","requestId","position","queueSize"}`，`requestId` 为 32 位小写 hex；
   - 名次前进逐条到达；同 (requestId, position) 不重复；
   - 放行 `{"sessionId","requestId","released":true}`，横幅消失、开始出字；
   - 网关日志按 `Chrys-Request-Attempt-Id` 能对上同一条请求（三处同值：主请求头、通知 requestId、cancel body）。
4. **中断验证**：排队中点「停止」→ iCode detail 日志出现「正在离开网关队列」，cancel body 的
   `request_id` 等于最后一条通知的 `requestId`；网关该队列元素出队。
5. **重试验证**：排队中断后重发，新通知的 `requestId` 与旧值不同，同名次也会重发（D2）。

## 7. 排障检查单（桌面端无横幅时按序排查）

| # | 检查 | 证据来源 |
|---|---|---|
| 1 | 桌面固定的 iCode 二进制是否含排队功能 | 版本号 / detail 日志有无「网关排队帧」 |
| 2 | 网关是否真的在下发 `event:queue_status` | iCode detail 日志 `aixcoding.detail.llm_queue` |
| 3 | 通知是否发出（方法名带 `_` 前缀） | 抓 ACP stdio JSON-RPC，找 `_chrys/queue_status` |
| 4 | `sessionId` 是否与桌面当前 prompt 绑定一致 | 桌面主进程 `[model-queue] bind` 日志 |
| 5 | 是否被去重吞帧（同 requestId+position 已发过、或 turn_started 未重置） | 对比通知序列与网关心跳 |
| 6 | 桌面端是否消费该通知（桌面侧责任） | `#handleModelQueueStatus` 断点/日志 |
