## 方案概述

建立一个正式、长期的探索批次，以“问题清单 → 只读调查 → 判别实验 → 能力分类 → 上游建议/实施输入”为工作流。六件文档承载探索范围和证据，`research/` 承载稳定主题结论，`experiments/` 承载可复现实验记录。

```text
旧版行为/上游机制/后台契约
          ↓
   研究问题与候选解释
          ↓
 只读源码、测试、Git 历史 + 必要黑盒实验
          ↓
 纯文件可做 / fork 必须改 / 建议上游通用能力 / 只能降级
          ↓
 后续实施批次独立 requirements、design、R2 签认与验证
```

本 design 仅授权探索方法和文档维护，不是任何实施功能或上游改动的批准。默认实验为只读调查、运行现有测试、分析现有 session/trajectory/mock 行为；若后续需要新增实验代码，只能落入定制目录并纳入 test-plan，不得借探索名义修改未获 R2 批准的上游文件。

## 备选方案对比

| 方案 | 优点 | 缺点 | 升级冲突面（文件数×行数×耦合度，R1） | 结论 |
|---|---|---|---|---|
| 一个正式探索批次，后续实施批次独立 | 讨论和实验有固定续接点；实施授权不被研究结论替代；符合批次平铺规范 | 探索期间需要持续整理，不能与实施 PR 混同验收 | 零产品代码、零上游接触 | **采用** |
| 直接按初步功能判断建立多个实施批次 | 看似能快速进入实现 | 开放问题会反复改变 R2 和批次边界，容易返工 | 未收敛即扩大上游接触面 | 暂缓，主要问题收敛后再裁决 |
| 只留聊天或临时调查材料 | 短期整理成本低 | 无法稳定续接、审查和形成上游沟通材料 | 无直接上游改动，但决策漂移风险高 | 否决 |

R1 自查：本批不实施业务逻辑，无上游接线；所有材料位于根 `aixcoding/docs/batches/` 定制开发资产目录。

## 对上游隐式行为的假设

| 假设 | 依赖方式 | 失效表现 |
|---|---|---|
| 研究基线为 fork 0.35.2，旧版对照为责任人本机留档的 0.28.0 终态副本 | 每篇研究文档标明基线和证据路径；本机绝对路径不是协作者/CI 通用契约，其他环境须自行定位等价副本 | 上游升级、旧副本路径或内容变化后，结论和引用行号必须重新核对，不自动沿用 |
| 上游源码、测试和 Git 历史可用于证明当前设计语义 | 只读调查并记录路径、行号、提交和测试 | 静态证据不能覆盖所有运行时组合，需用实验补齐并标明未证明事项 |
| 现有 session/trajectory/mock 可用于黑盒实验 | 优先分析真实产物、运行现有测试 | 字段缺失、版本漂移或样本不足时只能得出有限结论，禁止猜测 |

## 定制点登记预告

不适用：纯探索文档与实验记录，零上游接触、无产品代码定制点。后续实施批次必须独立登记，不得引用本节代替。

## 风险与最坏情况

- 把静态初查当成最终结论：通过状态标签、实验判别标准和未证明事项控制；关键 ID 和时序需要运行证据。
- 研究结论随上游升级漂移：所有主题记录基线；实施批次在当前基线重新验证 anchor。
- 探索文档变成共享 ROADMAP：只维护本批问题和续接点，各实施批状态由各自 plan 维护，全库全景由 `docs_report.py` 提供。
- 探索设计被误用为 R2 授权：本文明确不包含上游改动；任何实施批次独立签认。
- 回滚：本批为纯新增开发资产，删除目录即可回滚，不影响产品运行。
