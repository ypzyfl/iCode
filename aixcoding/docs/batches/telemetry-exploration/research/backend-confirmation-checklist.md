# 后台服务器改动确认单（telemetry 方案配套）

> **用途**：请后台团队逐项确认以下改动的可实现性与排期，书面回复。编号沿用客户端侧配套需求文档（BR-x），回复后由客户端侧对应回写。
>
> **背景**：AIxCoding CLI 将在新版本重建会话遥测上报（对齐 0.28 能力）。五类记录必须以**同一个 requestId** 关联：原模型调用记录、独立 LLM 报告、工具明细（tool-detail）、代码修改报告（ai-code）、ACP 最终响应身份。该 ID 取自**最终成功模型响应所属 HTTP 请求头 `Chrys-Request-Attempt-Id`**（下称 A-final），客户端上报该 ID 的**原值（32 位小写十六进制文本），不做 UUID 转换**（2026-11-18 责任人裁决）。关联结构：
>
> ```text
> 原模型成功记录(A 原值) ←—join—→ 独立 LLM 报告(A 原值)
> tool-detail：requestId=A1 原值，funcId=工具执行ID 原值
> ai-code：  requestId=A1 原值，reportId=工具执行ID 原值
> ACP 最终响应 _meta：requestId=A2 原值
> （A1=产生工具调用的成功响应；A2=工具执行后产生最终回答的成功响应）
> ```
>
> **现状**：BR-1~BR-5 曾于 2026-11-16 经问答确认目标态"可以，即使现在不可以，也可以改"（BR-1/BR-5 后经 2026-11-18 修订，按本文新版为准）；本文请提供书面确认与大致排期。BR-6/BR-7/BR-9/BR-10 尚未正式确认（BR-8 已于 2026-11-19 撤销，不在本单）。

## 零、已确认口径（无需重复确认，仅供对齐）

- 客户端上报什么，服务器按上报值记录；无需服务器另造或二次加工任何业务 ID。
- 服务器**无需**识别或聚合客户端的 SDK retry、redirect、Responses 轮询等机制，**也无需判定哪次请求"实际成功"**：每次请求的记录保存该次请求自己的 attempt header（BR-1），成功语义由客户端独立 LLM 报告 join 声明（BR-1/BR-6）。
- 无同一逻辑调用的多 HTTP 行聚合需求；若网关本身保存中间/失败 attempt，其口径见 BR-10。

## 一、致命项（P0）：任一不落实，telemetry 方案整体失败不可行

### BR-1 原模型调用记录保存每次请求自身的 attempt ID（不做成功判定）

**改动要求**：大模型调用记录的 requestId 字段，从读取请求体 `telemetry.requestId`（旧行为）改为读取**该次请求自己的**请求头 `Chrys-Request-Attempt-Id` 并落库。**服务器不需要、也不应该判断哪一次请求"实际成功"**（HTTP 200 + 业务错误、流式中断、Responses pending 等场景无法在服务器侧可靠判定）：

- 每个到达的请求各存自己的 attempt ID（失败、pending、流中断等中间请求按既有日志规则照常保留）；
- 成功语义由客户端的**独立 LLM 报告（BR-6）声明**：报告携带成功响应的 attempt ID（原值 32hex），查询/分析时与哪条记录的 attempt ID 一致，哪条就是该逻辑调用的成功记录——SDK retry 场景自然命中最终成功那次、Responses 场景自然命中最终 retrieve 那次，服务器无需理解这些机制；
- 每条记录的 attempt ID 必须是该次请求自己的 header 值，不得复用其他请求的值或另造 ID。

**不改的后果**：模型调用记录没有与客户端其他四类记录一致的 ID——五类记录 join 闭环不存在，方案核心失败。唯一替代路线要求客户端重新向请求体注入 ID 并新增全局逻辑调用头（上游与后台改动都更大），属已否决的回退方案。

**验收要点**：①SDK retry 429(A1)/成功(A2) 两条记录各存自己的 attempt；②Responses create pending(A1)/retrieve 成功(A2) 两条记录各存自己的 attempt；③独立报告携带 A2 原值时查询能 join 到 A2 记录而非 A1；④流式与并发请求不串号；⑤格式与原值要求见 BR-5。

**现状**：2026-11-16 口头确认可改读 attempt header；**2026-11-18 语义修订**：服务器不做成功判定（义务减轻）。请按本版书面确认 + 排期。

### BR-5 ID 原值保存（2026-11-18 责任人裁决：不转 UUID）

**改动要求**：所有 ID 字段**保持客户端原值**（32 位小写十六进制文本，如 `00112233445566778899aabbccddeeff`），不做 UUID 归一化/格式化：

- 原模型调用记录：直接保存该次请求 `Chrys-Request-Attempt-Id` 的原值；
- 独立 LLM/tool-detail/ai-code 等入口：requestId/funcId/reportId/spanId/parentSpanId 均为原值 32hex，服务器按原值保存，不另造、不转换、不截断；
- 全局唯一性由客户端保证（上述 ID 均为 128-bit 随机值，工程上满足全局唯一）；
- 后台需确认：①各入口/库表/校验**接受 32hex 文本**（无 UUID 格式强制、无长度/字符集限制）；②与既有 UUID 文本格式的 0.28 历史数据**新旧混存不冲突**（不要求迁移）；③查询、合并、组合幂等键统一使用原值文本。

**配套（桌面侧，客户端自行落实）**：Agent Studio `ModelRequestIdSchema`（现为 `z.string().uuid()`）需放宽接受 32hex——ACP 最终响应 `_meta` 将携带原值 requestId。

**不改的后果**：任一入口强制 UUID 格式则原值被拒 → join/消费失败；届时回评（放宽格式约束或重新引入转换层）。

**验收要点**：①各入口按 32hex 原值落库；②查询/幂等键使用原值文本；③新旧格式数据并存查询无冲突；④ACP `_meta` 原值通过桌面 schema。

**现状**：2026-11-18 责任人裁决（所有 ID 保持原值，不转 UUID）。请按本版书面确认 + 排期。

### BR-6 新增独立 LLM 报告保存接口

**改动要求**：新增独立 LLM 遥测报告保存接口（建议 `POST /csas/telemetry/api/v1/llm-report/save`）。这是**新接口新增**，非现有接口改造。最小报文 envelope（字段集可协商，接口存在性不可替代）：

```json
{
  "schemaVersion": 1,
  "sessionId": "…",
  "eventType": "llm",
  "eventSubType": "success",
  "requestId": "00112233445566778899aabbccddeeff",
  "spanId": "…",
  "parentSpanId": "…（可选，仅真实嵌套对话轮携带）"
}
```

- requestId 单键原子幂等：语义相同重放返回 200 不新增记录；同键不同内容返回 409；缺字段/非法值 400；
- 与原模型成功记录可通过 requestId join。

**不改的后果**：独立 LLM 报告无处发送，"原调用接口 + 独立报告"的组合路线失败；唯一替代是把遥测重新搭车进模型请求体（上游接触面大、已知存在旧缺陷），属已否决的回退方案。**另注（2026-11-18 BR-1 修订后）**：独立报告同时是成功语义的唯一声明源——哪条原模型记录被报告 join 命中，哪条即该逻辑调用的成功记录，故本项与 BR-1/BR-5 为绑定 P0。

**验收要点**：①新接口可接收最小 envelope 并落库；②重放 200 / 冲突 409 / 非法 400；③与原模型记录 join 查询可用。

**现状**：暂按客户端侧拟定的开发期契约执行，后台现网未确认。**请重点确认接口可新增。**

## 二、重要项（P1）：不落实方案仍可运行，但复杂度/数据质量显著恶化

### BR-2 工具明细单次终态保存

**改动要求**：tool-detail 接受**单次终态快照保存**（含最终 codeStatus、成功/失败信息等 final 字段），无需 PENDING→final 两阶段更新。

**不改的后果**：客户端退回两阶段 save(PENDING)+update(final)：短时间内连续两次写（后台已确认不宜）、存在中间态窗口。

**验收要点**：①单次 final save 落库即终态；②final-only（无前置 PENDING）不再失败。

### BR-3 `(requestId, funcId)` 组合键原子幂等

**改动要求**：tool-detail 以 `(requestId, funcId)` 建数据库唯一约束或原子 upsert——顺序或并发的重复保存只形成一条记录。

**不改的后果**：现状为裸插入（已确认无唯一索引）：重复 save 插重复行、update 命中全部重复行。客户端需以"同一执行至多保存一次、不重试"纪律硬性规避，传输抖动/超时重试场景下重复数据无数据库层防护。

### BR-4 重放与冲突语义

**改动要求**：相同组合键、相同终态内容的重放返回 200 且不改动事件时间/状态/结果；相同组合键、不同终态内容返回明确冲突（如 409），不隐式覆盖。

**不改的后果**：现状重复 final 会改写字段与完成时间（已确认非严格幂等），重试场景污染统计。

### BR-7 ai-code 幂等与 DTO

**改动要求**：ai-code 沿用 `reportId=工具执行ID 原值`，`(requestId, reportId)` 原子幂等，响应语义同 200/409/400；最小字段集 reportId/requestId/sessionId/spanId/filepath/blocks/sourceType/inputMethod/codeStatus，未知字段不静默接收。

**不改的后果**：ai-code 重复报告无防护，字段边界不一致。

### BR-9 取消/中断场景口径

**改动要求**：明确 cancelled/interrupted 工具调用的 codeStatus/failureType 映射（或明确声明不支持、客户端侧跳过），不得误归普通成功/失败。

**不改的后果**：客户端对取消场景只能统一跳过，统计完整性下降（旧版本即存在中断误报成功的问题，本次重建希望一并修正）。
