# 补充设计：区分测试打包和正式发布

- 责任人：兰荣达
- 状态：已确认
- 确认日期： 2026-11-17
- 确认意见：已确认

## 方案

在 CD 的 Run workflow 表单用一个下拉框选择打包用途。三种动作互斥。

| 选项 | 行为 |
| --- | --- |
| 测试打包（默认） | 跑 CI 和构建，支持单平台或全平台。安装包保存在本次 Actions 的 Artifacts。跳过 Tag 和 GitHub Release 写入。 |
| 正式发布 · 更新已有 Release | 从版本分支构建，覆盖 `v<版本>` 的同名附件，沿用桌面端下载地址。Release 不存在或不可修改时退出。 |
| 正式发布 · 创建新版本 | 从版本分支构建，创建 `v<版本>` Tag 和正式 Release。Tag 指向本次构建 SHA。Tag 或 Release 已存在时退出。 |

两个正式选项要求 `all` 平台，并复用现有版本分支命名规则和触发 SHA。目标版本须与 wheel 版本一致，版本号由构建版本决定。构建前检查目标 Release 或 Tag 是否符合所选动作，写入前再次核验。全平台包和 wheel 均齐备后，按桌面端现用文件名生成安装包及对应 `SHA256SUMS.txt`，并生成包含构建 SHA 与运行链接的 `BUILD_INFO.md`。

对目标版本的附件更新串行执行。仅替换本次构建对应的同名附件，保持 Release 的 Tag、标题、正文及发布状态。桌面端仍从原地址下载。Tag 对应的 GitHub 源码归档仍反映原 Tag；本次二进制来源以 `BUILD_INFO.md` 为准。

## 备选方案

| 方案 | 取舍 |
| --- | --- |
| 用一个下拉框选择打包用途（推荐） | 复用一套构建，测试是默认动作，更新和首次发布均须显式选择。 |
| 保留现有构建入口，人工下载并上传附件 | 改动小，但每次都要手工核对平台、版本、文件名与校验和。 |
| 每次创建新的预发布 Tag | 每次构建都有独立地址，桌面端需要随构建改版本配置。 |

## 上游改动清单（R2）

| 文件 | 修改范围 |
| --- | --- |
| `.github/workflows/cd.yml` | 在手动触发输入、构建引用解析、版本校验和发布 job 接入三种动作，校验 Tag、Release 和附件。复用现有 CI、wheel 与矩阵构建。新增接线按 R3 登记。 |

## 验收与回退

- 验证默认测试打包产出 Artifacts，且即使选到 Tag 也不会写入 Release。验证两种正式动作、当前与后续版本、分支与 wheel 版本不符、正式模式选择单平台、更新目标缺失或不可修改、新建目标已存在及附件缺失。失败场景在写入前退出。
- 用模拟制品验证全平台安装包的实际下载文件名及校验和。现有 Tag 和 PyPI 路径与新手动选项的兼容性单独验证。首次联调分别核对附件更新权限、新建 Tag 权限以及 Release 发布权限。
- GitHub 的逐个附件上传不是原子操作。上传前准备完整制品集，校验文件最后上传；出现部分更新时保留原产物供恢复，并用同一套产物重试或恢复上一整套附件。实际覆盖 Release 须由操作者显式触发。
