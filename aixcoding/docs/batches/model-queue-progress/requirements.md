# 需求：排队进度提示（model-queue-progress）

> 活文档：随时更新、不签认（git 留痕）；意图确认由 design 签认承载。

## 背景与问题

`model-queue-client` 批次已让客户端在网关排队时不再失败、也不会被 stall 看门狗误杀，但**没有任何可见反馈**：TUI 只有 WaitingRow 的呼吸点（无文案）、CLI 无输出、ACP 前端收不到任何通知。用户遇到长排队时看到的是"卡住了"，无法判断是在等模型资源。

## 目标与非目标

- 目标：排队期间在 TUI、CLI、ACP 三个前端都显示"排队中，前方 N 个请求"，放行后提示自动消失；被拒时沿用既有错误路径。
- 非目标：不实现取消排队（断连即出队）；不做预计等待时间估算（网关不提供）；不改网关协议；不改 `model-queue-client` 已定的帧判据与重译语义。

## 用户场景

1. TUI：发起提问后转写区的等待行变为「排队中，前方 3 个请求」，名次前移时文案更新，放行后恢复呼吸点。
2. CLI（`aicode run`）：排队时输出一行 `• 排队中，前方 3 个请求`（名次变化才再输出，避免刷屏）。
3. ACP（插件/桌面端）：收到 `chrys/queue_status` 通知，可在会话 UI 展示进度。

## 验收标准

- [ ] 网关下发 `queue_status` 时，TUI 等待行显示 position 与 queueSize（后者以「共 M 个」呈现），position 为 0 时文案为"正在获取模型资源"；`queueSize` 缺失或为 0 时省略总数。
- [ ] 无排队时等待行行为与改造前完全一致（不显示任何新增文案）。
- [ ] CLI 在名次未变化时不重复输出；放行后不输出残留。
- [ ] ACP 客户端收到 `chrys/queue_status`（字段含 position/queueSize/sessionId）。
- [ ] 排队帧到事件的转换失败（订阅方异常）不会中断 LLM 流。
- [ ] 三个前端在未订阅/未接线时互不影响。

## 开放问题

- ~~网关 `queueSize` 是否要在 UI 展示~~ 已决（2026-11-19）：展示。TUI/CLI 文案为「排队中 · 前方 N 个请求 · 共 M 个」，ACP payload 原本已带 `queueSize`；`queueSize <= 0` 时省略总数部分。
