# 模型排队桌面端透传说明

> 面向：桌面端（agent_studio_new）开发联调、iCode 排队功能的排查与验收。
> **线上契约的权威版本是同目录《模型排队通知协议规范.md》**（外发标准，引擎中立）；本文是 iCode 侧的
> 集成文档，含实现链路与内部细节，不要直接外发给其他引擎团队。
> 现行口径：`model-queue-progress` design v1.4–v1.6（2026-11-25 签认并实施；v1.6 的 QUEUE_FULL 通知延期，见 §3.1 注）。
> 关联文档：本目录 `requirements.md`（总口径）、`intranet-verification.md`（内网步骤）、
> `../batches/model-queue-progress/design.md`（实现设计与签认）。

## 1. 一句话结论

iCode 在网关排队期间通过 ACP 扩展通知 **`_queue_status`** 把排队状态透传给桌面端；载荷含
`requestId`（该次请求的 `Chrys-Request-Attempt-Id`）与单字段三态 `status`（「排队中」/「放行」/「拒绝」，v1.7），
拒绝帧另带 `reason`/`message`/`traceId`。

> **方法名迁移（2026-11-25 责任人裁决，iCode 已实施 design v1.5）**：跨引擎标准名 **`_queue_status`**
> （去 chrys 命名空间），权威契约见《模型排队通知协议规范.md》。**现版桌面端注册的仍是旧名
> `_chrys/queue_status`**——桌面端须先双注册两个方法名（先例：`chrys/error` 双拼写）再上含 v1.5 的
> iCode 构建，稳定后移除旧名注册；顺序不可倒，否则排队横幅消失。

## 2. 链路全景

```
网关（FIFO 队列）
  │ SSE event:queue_status {position, queueSize}（约 20s 心跳）
  ▼
iCode wire 层 guard_queue_frames（定制包，吸收帧、续活看门狗）
  │ QueueStatusTracker.observing 转发时回填 request_id          ← v1.4
  ▼
WireCallObserver.on_queue_status → EventBus GatewayQueueStatus（session 级事件）
  │ TUI WaitingRow 文案 / CLI 追加行（均不读 request_id）
  ▼
ACP server.py 挂点 → ext_notification("queue_status", payload)
  │ Python ACP SDK 发送时自动加 "_" 前缀（acp/agent/connection.py:206）
  ▼
线上方法名 = _queue_status
  ▼
桌面端 chrys-protocol.ts:63 注册 → #handleModelQueueStatus 校验载荷
  → bindPrompt 绑定会话 → model-queue service（source='engine'）
  → 渲染层排队横幅（ConversationPane.vue，与 Pi 代理路径共用同一 UI）
```

要点：

- **方法名的 `_` 前缀不是拼写差异**：iCode 代码写 `queue_status`，SDK 在 JSON-RPC 发送层
  自动加 `_`（扩展方法约定）；桌面端改造后注册 `_queue_status` 即与线上一致（迁移注记见 §1）。
- `sessionId` 是路由键（`session/new` 返回给桌面端的会话 id），桌面端靠它把通知绑到当前 prompt；
  缺失该键整条通知会被桌面端丢弃——**不能**用 `requestId` 取代。

## 3. 载荷契约（v1.5–v1.7 三帧；权威版本见协议规范 §3）

### 3.0 原始 JSON-RPC 帧（其他引擎照此发）

ACP stdio 为**换行分隔**的 JSON-RPC 2.0（每帧一行，无 Content-Length 头）；通知帧无 `id` 字段。
方法名在**线上必须带 `_` 前缀**（ACP 扩展方法约定）：`_queue_status`——Python ACP SDK 调
`ext_notification("queue_status", …)` 时自动加；其他引擎若手写 JSON-RPC 或所用 SDK 不自动加，
须写字面名 `_queue_status`。

排队中（一行一帧）：

```json
{"jsonrpc":"2.0","method":"_queue_status","params":{"sessionId":"<会话id>","requestId":"<32位小写hex>","status":"排队中","position":2,"queueSize":5}}
```

放行（一行一帧）：

```json
{"jsonrpc":"2.0","method":"_queue_status","params":{"sessionId":"<会话id>","requestId":"<32位小写hex>","status":"放行"}}
```

拒绝（一行一帧，v1.6；iCode 现只发 `QUEUE_TIMEOUT`，`QUEUE_FULL` 延期）：

```json
{"jsonrpc":"2.0","method":"_queue_status","params":{"sessionId":"<会话id>","requestId":"<32位小写hex>","status":"拒绝","reason":"QUEUE_TIMEOUT","message":"<网关原文>","traceId":"<网关追踪id>"}}
```

`requestId` 未知时**省略该键**（不是 null/空串）。键序不应被消费方依赖。

### 3.1 字段与时机

| 通知 | 载荷 | 时机 |
|---|---|---|
| 排队中 | `{sessionId, requestId, status:"排队中", position, queueSize}` | 每个 (requestId, position) 首次出现 |
| 放行 | `{sessionId, requestId, status:"放行"}` | 排队后首个数据帧到达，一次 |
| 拒绝 | `{sessionId, requestId, status:"拒绝", reason, message?, traceId?}` | 队列原因终结本轮时一次，不去重（v1.6） |

> v1.7（2026-11-25，同事反馈）：相位由 v1.0 的 `(released, rejected)` 布尔对改为**单字段 `status`
> 三态枚举（中文值）**；iCode 侧仅 `queue_notify.py` 载荷构造与测试断言变化，内部模型（position/rejected
> 字段）不动，`server.py` 挂点零改动（v1.6 整体传 event 的红利）。

> 实施注记：QUEUE_FULL 的耗尽挂点在 wire 重试层（kernel 核心热点），超出 v1.6 限定规模，
> 按变更单预授权**延期**（规范已支持，iCode 暂只发 QUEUE_TIMEOUT；FULL 耗尽表现为普通错误，与现状一致）。
> 拒绝帧**不带最后已知 position/queueSize**（规范标可选）：带则 TUI/CLI 的放行清屏逻辑会把拒绝当
> 排队帧刷新文案，需改上游 handler——不值得；拒绝帧 position=-1 走既有清除路径。

字段语义：

- **sessionId**：会话 id，值与语义不变；桌面端横幅路由键。
- **requestId**：应答该次请求的 HTTP 尝试所带的 `Chrys-Request-Attempt-Id` 请求头值（32 位小写 hex）
  = 网关队列元素键 = iCode 调 cancel 接口时 body 里的 `request_id`。**每个 HTTP 尝试一个新值**：
  SDK 重试/重定向、wire 重试、整轮重试各算一个；一个 turn 内多次模型调用会出现多个。
- **requestId（必填，2026-11-25 责任人裁决）**：iCode 产品路径恒有（每个 HTTP 尝试必带
  `Chrys-Request-Attempt-Id` 请求头）。tracker 未武装（绕过生产 HTTP 客户端的裸客户端）时省键——
  该路径按《模型排队通知协议规范.md》v1.0 属契约外，改造后消费方丢帧（非产品路径，无可见影响）。
- **去重**（D2：键含 requestId）：同一 (requestId, position) 只发一次（网关心跳重复同名次被吞）；
  重试产生新 requestId，即便同名次也重发——保证桌面端手上的 id 永远是活请求的。
  `chrys/turn_started` 重置去重（中断后下一轮不被残留值吞帧）。
- 桌面端不应依赖 JSON 键序。

## 4. 版本配套矩阵

| 组合 | 行为 |
|---|---|
| 新 iCode（v1.4）+ 现版桌面端 | 多出的 `requestId` 被忽略，横幅照常（现版处理器只读已知键） |
| 新 iCode（v1.4）+ 改造后桌面端 | 按请求粒度消费 `requestId`（桌面端同步改造，非本仓范围） |
| 旧 iCode（三字段，无 `requestId`）+ 改造后桌面端 | 契约外，桌面端丢帧、无横幅——升级 iCode |

## 5. 桌面端展示口径（统一文案，2026-11-25 责任人要求）

**提示词以 iCode 代码（`queue_note`）为唯一口径，桌面端不得有第二套文案**（权威定义见
《模型排队通知协议规范.md》§6）。现版桌面实现（2026-11-24 实核）与统一口径的差异如下，须改造对齐：

| 项 | 统一口径（目标） | 现版桌面实现（须改） |
|---|---|---|
| position ≥ 1 | 「当前模型请求量大，请求排队约 N 人」，**N=position**，无后缀 | N 取 queueSize（总长），且带「请稍候或切换至其他模型」后缀 |
| position = 0 | 「已排到队首，当前为队列第一位」 | 「正在获取模型资源…」（position 0 ≠ 已获资源，design v1.2 定性，该文案承诺过头） |
| 排队超时/队满 | **不走排队横幅**（rejected 横幅仅 Pi 代理路径可达；engine 通知只有 queued/released 两相） | 同左（iCode 的 QUEUE_TIMEOUT 表现为普通 turn 失败报错） |
| 「取消排队」按钮 | 现版为 Pi 代理专用（依赖代理注册的取消详情，engine 路径返回 not_found） | iCode 的网关取消走「停止」按钮（session/cancel → iCode 补发 cancel，v1.1 实现）；桌面端改造后可用 requestId 自行调 cancel 接口 |
| 放行 | released 通知到达，横幅消失，随后开始流式出字 | 一致 |

## 6. 联调步骤

前提：桌面端只运行 `applicationConfig.icode.binaries` 固定的 iCode 构建——**须指向含排队功能的本分支构建**，
否则横幅不会出现。

1. **本地模拟**（无网关）：`mock_server/model_concurrency_verify/`（仓外未跟踪资产）起 mock 网关，
   `-m QueueMock` 模式下发排队帧；iCode 侧用 TUI/CLI 先自查三端文案（见 `intranet-verification.md` §2–3）。
2. **桌面端连通**：桌面指向上述构建 + mock/内网网关，发起会占到并发槽位的请求。
3. **观察通知**（桌面主进程日志 `[model-queue] event queued <appSessionId> <position>`，或抓 ACP stdio）：
   - 排队中 `{"sessionId","requestId","position","queueSize"}`，`requestId` 为 32 位小写 hex；
   - 名次前进逐条到达；同 (requestId, position) 不重复；
   - 放行 `{"sessionId","requestId","released":true}`，横幅消失、开始出字；
   - 网关日志按 `Chrys-Request-Attempt-Id` 能对上同一条请求（三处同值：主请求头、通知 requestId、cancel body）。
4. **中断验证**：排队中点「停止」→ iCode detail 日志出现「正在离开网关队列」，cancel body 的
   `request_id` 等于最后一条通知的 `requestId`；网关该队列元素出队。
5. **重试验证**：排队中断后重发，新通知的 `requestId` 与旧值不同，同名次也会重发（D2）。

## 7. 排障检查单（桌面端无横幅时按序排查）

| # | 检查 | 证据来源 |
|---|---|---|
| 1 | 桌面固定的 iCode 二进制是否含排队功能 | 版本号 / detail 日志有无「网关排队帧」 |
| 2 | 网关是否真的在下发 `event:queue_status` | iCode detail 日志 `aixcoding.detail.llm_queue` |
| 3 | 通知是否发出（方法名带 `_` 前缀） | 抓 ACP stdio JSON-RPC，找 `_queue_status` |
| 4 | `sessionId` 是否与桌面当前 prompt 绑定一致 | 桌面主进程 `[model-queue] bind` 日志 |
| 5 | 是否被去重吞帧（同 requestId+position 已发过、或 turn_started 未重置） | 对比通知序列与网关心跳 |
| 6 | 桌面端是否消费该通知（桌面侧责任） | `#handleModelQueueStatus` 断点/日志 |
