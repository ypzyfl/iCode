# 模型排队通知协议规范（`_queue_status`）

> **协议版本**：v1.1（2026-11-25；v1.0 同日首发后被同事反馈修订）
> **适用范围**：任何经 ACP（stdio）接入桌面端（AIxCoding / agent_studio）并支持网关模型排队的引擎。
> 本文件是线上契约的唯一权威版本；iCode 的实现细节见同目录《模型排队桌面端透传说明.md》。
> 渲染文案执行 §6 **统一提示词**（与 iCode 代码一字不差，2026-11-25 责任人要求）；
> 文案之外的呈现形式（横幅样式、位置）由消费方自定。

## 1. 传输层

- 通道：ACP stdio，**换行分隔的 JSON-RPC 2.0**（每帧一行，无 `Content-Length` 头）。
- 帧类型：**notification**（无 `id` 字段，无响应）。
- 方法名：**`_queue_status`**。下划线前缀是 **ACP 协议对「扩展方法」的约定标记**（SDK 路由靠它
  识别并安全忽略未知扩展），不属于任何引擎品牌；`queue_status` 为跨引擎标准名
  （2026-11-25 责任人裁决：去 chrys 命名空间，供所有引擎统一使用）。
  - Python ACP SDK：调 `ext_notification("queue_status", …)`，SDK 自动加前缀。
  - 手写 JSON-RPC 或所用 SDK 不自动加前缀的引擎：**必须写字面名 `_queue_status`**。

## 2. 帧定义

### 2.1 排队中（每个名次变化发一次）

```json
{"jsonrpc":"2.0","method":"_queue_status","params":{"sessionId":"<会话id>","requestId":"<32位小写hex>","status":"排队中","position":2,"queueSize":5}}
```

### 2.2 放行（排队结束发一次）

```json
{"jsonrpc":"2.0","method":"_queue_status","params":{"sessionId":"<会话id>","requestId":"<32位小写hex>","status":"放行"}}
```

### 2.3 拒绝（队列原因最终杀死了本轮，发一次）

排队超时：

```json
{"jsonrpc":"2.0","method":"_queue_status","params":{"sessionId":"<会话id>","requestId":"<32位小写hex>","status":"拒绝","reason":"QUEUE_TIMEOUT","message":"<网关原文>","traceId":"<网关追踪id>"}}
```

队列满拒绝（引擎重试耗尽、整轮被它终结时）：

```json
{"jsonrpc":"2.0","method":"_queue_status","params":{"sessionId":"<会话id>","requestId":"<32位小写hex>","status":"拒绝","reason":"QUEUE_FULL","message":"<网关原文>","traceId":"<网关追踪id>"}}
```

## 3. 字段规范

| 字段 | 类型 | 必填 | 约束 | 语义 |
|---|---|---|---|---|
| `sessionId` | string | **必填** | 非空；必须是 `session/new` 返回给桌面端的会话 id | 路由键：桌面端靠它把通知绑定到当前会话；**缺失或为空 → 整帧被丢弃** |
| `requestId` | string | **必填** | 32 位小写 hex；缺失或非法（`null`/空串/非该格式）即契约外 | 本次排队请求在网关队列中的元素键（iCode 取 `Chrys-Request-Attempt-Id` 请求头值）；每个 HTTP 尝试一个新值 |
| `status` | string | **每帧必填** | 枚举：`"排队中"` / `"放行"` / `"拒绝"`（v1.1：同事反馈，替代 v1.0 的相位布尔对；值域外整帧丢弃） | 相位标志，单字段三态 |
| `position` | int | 排队帧必填；放行/拒绝帧**可选** | 整数，`0 ≤ position ≤ 1_000_000`；可选时为本请求**最后已知**名次（引擎知道才带，不得伪造） | 前方排队请求数；`0` = 已排到队首（**不等于已获得模型资源**，仍可能排队超时） |
| `queueSize` | int | 排队帧必填；放行/拒绝帧**可选** | 整数，`0 ≤ queueSize ≤ 1_000_000`；可选时为最后已知队长 | 队列当前总长 |
| `reason` | string | 拒绝帧必填 | 枚举：`QUEUE_TIMEOUT` / `QUEUE_FULL`（可扩展，消费方遇未知枚举丢帧） | 拒绝原因，映射 §6 拒绝文案 |
| `message` | string | 拒绝帧可选 | 网关原文消息（诊断用，非渲染文案） | 排障与日志对齐 |
| `traceId` | string | 拒绝帧可选 | 网关追踪 id（服务端链路追踪，报障对齐） | 与网关日志对齐 |

通用规则：

- **相位由单字段 `status` 判定，每帧必填**（v1.1：同事反馈将 v1.0 的 `(released, rejected)` 布尔对
  合并为一个字段；责任人裁决枚举值用中文）：`"排队中"` 须带 `position`/`queueSize`；`"放行"` 与
  `"拒绝"` 不强制携带（可选带最后已知值）；值域外 → 契约外，整帧丢弃。
- `message`/`traceId` 仅拒绝帧出现：网关的位置帧数据不含它们、放行帧为客户端合成——**无数据来源的
  字段不造值**。
- `sessionId` 缺失/为空、数值越界、任何帧形都不满足 → **整帧被桌面端静默丢弃**。
- 消费方不得依赖 JSON 键序。

## 4. 发送方义务（引擎侧；桌面端不去重，以下全是发送方责任）

1. **只在活跃 prompt 期间发送**：桌面端按会话+当前 prompt 绑定路由，prompt 结束后的通知无处安放。
2. **心跳去重**：网关约 20s 心跳会重复同名次，引擎必须自行抑制——每个 `(requestId, position)` 组合只发一次。
3. **名次前进即发**：position 变化是新事实，立即发新帧。
4. **放行恰好一次**：排队结束后发一次 `status: "放行"`，与排队帧同 `requestId`；从未排队则什么都不发
   （不要发 `position:0` 假帧来表示"开始了"）。
5. **新请求必须重发**：重试/新调用产生新 `requestId`，即便落到同名次也要重发——保证消费方手上的
   `requestId` 永远指向活请求（可用于对齐网关日志、调 cancel 接口）。
6. **轮次边界重置**：新 turn 开始时清空去重状态；建议同时发 `_chrys/turn_started`（iCode 行为），
   消费方也以它为兜底重置。
7. **拒绝帧时机**（2026-11-25 责任人裁决，两 reason 语义不同）：
   - `QUEUE_TIMEOUT`：轮次因它终结时**即发一次**（终态不重试）；
   - `QUEUE_FULL`：**仅当引擎重试耗尽、整轮被它终结时发**——重试进行中不发（重试期间的等待由
     消费方的重试状态显示覆盖；发早了会出现「已满」横幅后回答照常流出的乌龙）；
   - `QUEUE_CANCELLED`（用户排队中主动中断）**不发**：用户已知情，横幅随 prompt 结束消失。
8. **拒绝即终帧**：同一 `requestId` 的拒绝帧之后，本轮不再有任何该 id 的帧。

## 5. 消费方解析规则（桌面端）

现版行为（`acp-agent-host.ts` `#handleModelQueueStatus`）：

1. `sessionId` 非空 string，否则丢帧；
2. 相位按 `status` 单字段判定：`"放行"` 清横幅；`"拒绝"`（`reason` 须为已知枚举，否则丢帧，渲染 §6
   拒绝文案；可选的 `position`/`queueSize` 若带须过数值校验）；`"排队中"` 须过第 3 条数值校验；
   值域外丢帧。**现版桌面端没有 `status` 概念**（只认 v1.0 前的 `released` 布尔与 position 分支），
   须同步改造；
3. 排队相位下 `position`、`queueSize` 均须为整数且在 `[0, 1_000_000]`，否则丢帧；
4. 通过校验后按 `sessionId` 找当前 prompt 绑定，映射为会话级排队视图（横幅显示/消失）；
5. 未知字段（未来新增字段）被忽略，不因多余键丢帧。

**现版桌面端没有拒绝分支**：拒绝帧无 `position`，会被当排队帧校验失败而**静默丢弃**——拒绝相位的
展示需桌面端同步改造（其 rejected 横幅与 reason→文案映射现成，只差接 engine 来源）。

改造后（按 `requestId` 消费，2026-11-25 责任人裁决）：`requestId` 为必填校验项——缺失或非法
（非 32 位小写 hex）**整帧丢弃**，不回退按 `sessionId` 展示。

## 6. 统一提示词（渲染文案，与 iCode 代码一字不差）

排队期间消费方展示的文案以 iCode 代码（`queue_note`）为唯一口径，不得自造第二套：

| 相位（status 值） | 文案 |
|---|---|
| 排队中，position = 0 | `已排到队首，当前为队列第一位` |
| 排队中，position ≥ 1 | `当前模型请求量大，请求排队约 {position} 人` |
| 放行 | 提示消失（无文案），随后开始出字 |
| 拒绝，reason = QUEUE_FULL | `当前使用人数较多，模型排队已满，请稍后重试。` |
| 拒绝，reason = QUEUE_TIMEOUT | `排队等待超时，请稍后手动重试或切换模型。` |

> 拒绝文案无 iCode 代码先例（iCode 自身以普通错误呈现），2026-11-25 以桌面端现有文案为底稿定稿；
> 改字由责任人裁决，改后本表为唯一口径。

硬性要求：

- **N 取 `position`（前方人数），不是 `queueSize`**；
- **不加任何后缀建议语**（如「请稍候或切换至其他模型」——iCode 2026-11-19 调整时已删除）；
- **position = 0 禁止写「正在获取模型资源…」**：`position=0` 是"下一个就轮到你"，不等于已获得
  模型资源，队首仍可能 `QUEUE_TIMEOUT`（iCode design v1.2 定性，该文案承诺过头）。
- 现版桌面端（2026-11-24 实核）三处均与此不同（队首文案 / N 取 queueSize / 带后缀），
  须按本节统一改造；`queueSize` 字段仍随载荷传递，供消费方自行做进阶展示（非文案）。

## 7. 兼容性矩阵

| 发送方 | 消费方 | 行为 |
|---|---|---|
| 带 `requestId`（契约内） | 现版桌面端 | 正常（现版忽略该键，横幅照常） |
| 带 `requestId`（契约内） | 改造后桌面端 | 正常（按请求粒度消费） |
| 缺 `requestId`（契约外） | 现版桌面端 | 正常（现版不读该字段） |
| 缺 `requestId`（契约外） | 改造后桌面端 | **整帧丢弃，横幅不显示**——发送方必须升级到本契约 |
| `requestId: null` / 空串 / 非法格式 | 任何 | **禁止这么发**；消费方按契约外丢帧 |
| 拒绝帧（`status:"拒绝"`） | 现版桌面端 | **整帧丢弃**——超时/队满以普通错误呈现 |
| 拒绝帧（`status:"拒绝"`） | 改造后桌面端 | 正常（rejected 横幅 + §6 拒绝文案） |
| 放行帧（`status:"放行"`） | 现版桌面端 | **被丢弃**（现版认 `released:true`）——横幅不再即时消失，随 prompt 结束消失；须改造 |

方法名迁移（v1.0 定名 `_queue_status`）：iCode **已于 design v1.5（2026-11-25 签认实施）切换**；
**现版桌面端仍只注册旧名 `_chrys/queue_status`**——桌面端须先**双注册**两个方法名（先例：`chrys/error`
与 `_chrys/error` 双拼写）再上含 v1.5 的 iCode 构建，iCode 切换稳定后再移除旧名注册。其他引擎直接按
本规范发 `_queue_status`。iCode 的拒绝帧现只发 `QUEUE_TIMEOUT`（`QUEUE_FULL` 耗尽挂点延期，
design v1.6 开放项裁决），规范对两 reason 均已定义。
