# 需求：并行批次编号与文档热点治理（parallel-batch-governance）

> 活文档：随时更新、不签认（git 留痕）；意图确认由 design 签认承载。

## 背景与问题

并行批次在 PR 合并时反复遇到两类相互放大的冲突：

1. **全局编号协调**：定制点 `C###` 按全库历史最大号加一分配，孪生组还占用连续区间；并行分支可能撞号，后合并方需要跟改 design、测试名和路线文档。`logo-branding` 批次还实证了历史单 id 无法扩成连续孪生区间的问题。
2. **共享文档写热点**：每个批次创建时都向 `INDEX.md` 追加一行；功能、升级和路线决策又共同更新 `ROADMAP.md`。文本冲突之后往往还伴随编号、状态、基线和关联批次的事实对账。

集中导航和路线记录本身有价值，问题在于把它们的载体设计成所有并行 PR 的同步写入点。责任人已裁决立项治理，并进一步明确：`INDEX.md` 与 `ROADMAP.md` 均随本批物理删除，历史内容从 Git 获取；迁移项由责任人自行跟踪，不在仓库另建替代台账。

## 目标

总目标不是追求“零冲突”，而是让剩余冲突尽可能落入 **AI 无需人工决策、可机械修复、可用门禁验证**的范围：

1. 新定制点和新 ADR 使用无需跨批次协调的稳定语义 ID，从源头消除全局抢号及改号后的关联 churn；ADR 全部进入全局池，来源批次由 ID 表达，存量功能池文档随规则生效迁入全局池。
2. 新批次不再为了登记自身而修改共享根文档；集中导航能力由按需只读视图提供。
3. 明确冲突分级和 AI 处置边界：普通并行新增由 Git/AI 直接合并；旧编号撞号按预授权算法机械转换；同一决策、同一行为或 R2 范围的实质分歧才交人裁决。
4. 机械修复只允许改未合并批次的已签 design 变更清单内的文件，不修改已合并侧、不重排历史、不做全库引用替换，并可用 `strict`、`check_docs` 和测试闭环验证。
5. `INDEX.md` 随规则生效物理删除：批次目录全景由 `docs_report.py` 提供，固定入口由 `aixcoding/README.md` 承载；有目录的微改动照常纳入，无目录微改动通过 GitHub merged PR 视图查询，不新增留痕义务、生成物 freshness 门禁或强制元数据迁移。
6. `ROADMAP.md` 随本批物理删除，不等待完整验收或旧分支归档，不保留退役标记、冻结档案、重定向或占位文件；迁移项由责任人自行跟踪，历史内容从 Git 获取。
7. 增加文档闭环门禁：草案决策档、批次必备文件缺失、ADR 引用断裂，以及结构化 plan 完成状态所引用的 self-review/verification 文件缺失或空壳不得进入主干；`guard-switches` 的未签 ADR 与缺失评审/验证文档作为本批存量修复验收项。
8. 规则、工具、模板和 ADR 在同一治理批次原子切换，避免未签认的临时规则与现行规范并行。

## 非目标

1. 不修改任何上游产品代码、上游测试或既有 marker，不改变 `(落点, marker 锚)` 对账主键。
2. 不全库重排旧 `C###` 或旧数字 ADR，不改写历史验证记录，不把 ID 写入上游 marker。
3. 不承诺自动解决产品行为、同一 ADR 决策、同一路线优先级或 R2 审批范围的语义冲突；这些必须停等责任人。
4. 不建设通用自动合并机器人，不采用 union/ours 等自动盲合策略，不以生成器重写整个文件来掩盖冲突。
5. 不为删除的 ROADMAP 建设 per-item 文件拆分、聚合系统、冻结档案或仓库内替代迁移台账。
6. 不提交生成式 INDEX，不增加 freshness 门禁，不要求给全部历史批次补 front matter、README 或其他导航元数据文件。
7. 不在本批补齐存量缺口封闭清单中的历史批次缺失文档；仅修复 `guard-switches` 的决策签认与评审/验证缺口。
8. 不把普通功能 PR 的 INDEX 缺行设为 CI 阻塞条件，不建立永久的逐批后置对账 PR 机制。
9. 不用自然语言猜测判定 plan 中所有“虚假完成陈述”，不以文件存在或最小形态通过替代实际评审/验证证据。
10. 不把批次目录全景扩张为全部改动统计，不要求无目录微改动补 `micro/` 或精简批次目录，不让 docs_report 联网、调用 GitHub API 或猜测微改动分类与数量。规则生效后，§6 豁免微改动不新建 `batches/` 目录；需要批次目录即走完整管线六件，不新增缺件目录豁免。

## 用户场景

1. 两个并行批次各自起草 design 和 ADR 时，以本批次目录为命名空间分配 ID；合并两侧后无需选号、改号或修改对方文件，校验直接通过。
2. 旧规则下两个未合并分支已经使用相同 `C###` 或 ADR 数字时，AI 保留已合并侧，只把另一侧机械转换为本批语义 ID，并在该批已签 design 变更清单内修复引用；无需责任人重新选号或重复签认，方案内容保持不变。
3. 新批次只在自己的目录写文档；需要查看全部有目录批次时运行只读导航命令，得到完整目录，不检查或更新一份集中表格；封闭清单覆盖的存量微改动目录即使只有 plan 也能导航。
4. 两个分支同时改变同一 ADR 的结论、同一路线优先级或同一上游触点的行为时，AI 不猜测业务意图，列出分歧并停等。
5. INDEX 与 ROADMAP 删除后，批次目录全景由命令生成，无目录微改动通过 GitHub merged PR 视图按描述人工识别，迁移项由责任人自行跟踪；需要查阅旧 INDEX/ROADMAP 内容时从 Git 历史获取，不恢复共享文件。

## 开放问题

1. INDEX 目标态：推荐随本批物理删除，批次目录全景由 `docs_report.py` 提供、固定入口并入 `aixcoding/README.md`。
2. 导航信息与边界：推荐直接复用现有文档 H1，不为保留“类型/一句话简介”而全量补元数据；已接受仅覆盖有目录批次，无目录微改动查 GitHub merged PR，不新增留痕义务。
3. ROADMAP 目标态：已裁决随本批物理删除，不保留冻结档案或重定向；历史内容从 Git 获取，迁移项由责任人自行跟踪。
4. 机械修复预授权：推荐仅对确定性保留字改号、固定顺序后缀分配且 `check_id_only.py` 可证明 ID-only 的变更免重复签认；旧区间/孪生组、歧义引用和任何语义变化仍停等。
5. 过渡方式：推荐本批原子切换，不先试行一套“功能 PR 不写 INDEX、合并后再补 INDEX”的临时双重流程。
6. 微改动增量路径：按已接受的导航边界，§6 豁免微改动不新建 batches 目录；需要目录即走完整管线六件，不新增缺件目录豁免。
