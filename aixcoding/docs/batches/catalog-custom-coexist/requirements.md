# 需求：后端同步模型与自定义模型共存

> 活文档：随时更新、不签认（git 留痕）；意图确认由 design 签认承载。

## 背景与问题

当前 `apply_catalog()`（`src/chrys/service/aixcoding/models/catalog.py`）在同步成功后
按 `final_names = {后端 id}.yaml` 删除目录里**所有**不在本次后端列表的 `*.yaml` /
`*.yml`。结果是：用户放在 `~/.chrys/models/` 里的自定义模型，只要后端目录里没有
同 id 项，下次同步就被无差别删除。mock README 里「自管模型文件不会被覆盖删除」
的承诺，在 auto_sync 开启后并不成立。

需求是让两者共存：**由后端同步写入的模型要随目录更新（含删除），用户自定义模型
不参与同步、不被删除**；且升级到本方案时，旧版同步写出的无标记残留能一次收敛。

## 目标与非目标

- 目标：
  1. 后端写盘时给每个模型 YAML 写入标记字段 **`synced_from_server: true`**，
     仅由同步逻辑读写，`ModelProfile` / loader 不感知、不新增 dataclass 字段。
  2. 同步更新时按标记区分：只删除「有标记 且 本次后端不再下发」的模型文件；
     无标记的自定义模型文件保留。
  3. 自定义模型文件在磁盘保留的同时进入内存快照：`install_snapshot` 装入
     「后端项 + 磁盘上保留的自定义项」，否则自定义模型磁盘在、TUI 里看不见。
  4. ID 冲突（自定义模型与后端模型同 id）：**后端覆盖**，且磁盘与内存两个层面
     都保持后端胜出（内存快照按 id 键入字典，保留项须先按后端 id 过滤）。
  5. 冲突与升级清空的告警载体：**仅 detail 日志**（责任人裁决：不做 TUI 主动提示）。
  6. 升级收敛（旧版同步写出的 YAML 无标记）：第一次同步时若目录中存在配置文件、
     但全部无标记且**全部探针可判定**，判定为旧配置，在**整个发布成功后**清空
     目录中文件名不在本次后端写入集合的无标记文件。后端已下架的旧模型因此不残留。
  7. 健壮性：单个畸形/不可读 YAML 文件不得中断整轮同步；无法判定的探针
     不得触发破坏性清空。
- 非目标（防止范围蔓延）：
  - **不依赖 `.catalog-state.json` 做标记判定**——该文件继续按现状写入，
    `profile_ids` 语义不变（仍只记后端 id），但同步逻辑不以它区分来源。
  - 不在 `ModelProfile` / `schema.py` / `loader.py` / `app.py` 加字段或解码，
    **零上游改动**。
  - 不改 TUI 只读门禁（保持恒只读，自定义模型继续走文件系统通道）。
  - 不引入「内容未变则跳过写盘」的优化——当前版本每次同步都全量重写，
    指纹只是记录（源码 docstring 明写），本批不改这一行为。
  - 不改后端 payload 契约、不新增配置项、不加第三方依赖。

## 用户场景

1. 用户在 `~/.chrys/models/` 放一个自定义 `my-model.yaml`（无标记），开启同步；
   某次后端下发新模型列表：自定义文件**仍在**，且 TUI 列表里可见、可选中发起
   会话（TUI 对模型配置恒只读，「可用」指可选中使用，不含编辑/新建）。
2. 后端某次下发的模型被移除：下次同步删除对应的 `synced_from_server: true`
   文件；用户自定义文件不受影响。
3. 用户自定义模型 id（文件名或 YAML 显式 id）与后端某模型相同：本次同步后端
   覆盖该文件（同名 `os.replace` 或显式 id 在内存中被过滤），全部完成后 detail
   日志记录覆盖原因。
4. 升级场景：目录里有旧版同步写出的无标记 YAML → 第一次同步判定为旧配置，
   发布成功后清空文件名不在本次后端集合中的无标记文件；detail 日志记清空计数。
   目录里混有畸形文件（探针不可判定）时不触发清空，照常写后端模型。
5. 目录里只有畸形的 YAML（全部探针 `None`）：不触发清空，同步不被中断，
   后端模型照常写入。

## 验收标准

- [ ] 后端写盘的每个模型 YAML 含 `synced_from_server: true`；解析该 YAML 的
      loader 不因该未知字段报错或把它塞进 `ModelProfile`。
- [ ] 同步删除只针对「有标记且不在本次后端列表」的文件；无标记文件全部保留
      （**除非触发首次升级清空**：目录有配置文件、全部无标记、全部探针可判定 →
      发布成功后清空文件名不在本次写入集合的无标记文件；空目录不触发；
      任一探针不可判定不触发）。
- [ ] 首次升级清空发生在 staging → `os.replace` → 陈旧删除 → `write_catalog_state`
      **全部成功之后**；任一前置失败旧文件原样保留、state 未重写、tmp 被清理，
      与常规两阶段「失败不碰旧数据」承诺一致；清空 detail 日志记精确计数。
- [ ] 自定义模型（无标记）在同步后仍出现在 `ModelProfileRegistry` 列表里；
      `install_snapshot` 调用前后零磁盘 IO（纯内存替换语义不变）。
- [ ] ID 冲突：判定以**文件名 stem**为准（非 YAML 显式 id）；后端覆盖自定义文件；
      内存快照中保留项按后端 id 集合过滤，显式 id 撞后端 id 的保留文件不覆盖
      后端项；detail 日志记录被覆盖 id 与原因（仅日志）。
- [ ] `.catalog-state.json` 内容与写入逻辑不变；同步判定不读取该文件的
      `profile_ids` 作来源区分。
- [ ] 指纹 `_coerce_version` 仍只含后端项、语义不变。
- [ ] 单个畸形 YAML：`synced_from_server` 探针以 `except Exception` 兜底返回
      「不可判定」，同步不中断、该文件按自定义保留。
- [ ] 既有 catalog 同步测试不回归；新增契约测试覆盖标记/保留/删除/冲突/告警/
      快照/升级清空/容错，关键 guard 有非 vacuous 证明。
- [ ] 治理门禁：design 签认、六件套齐、`check_docs --closure` 全绿、
      `gen_customizations --strict`、ruff 双检 / ty / Smart Test 全绿。

## 开放问题

- **TUI 提示挂点（已裁决）**：不做 TUI 主动提示，告警仅进 detail 日志。
  Textual 的 `notify()` 是 App/Widget 实例方法、`active_app` 是主线程
  ContextVar、EventBus 无全局单例，业务层无法直接发 toast；为最小化源码改动，
  本批不引入回调通道、不改 app.py。
- **升级迁移判据（已裁决）**：全无标记即判旧配置、发布成功后清空一次。
  曾考虑「state 存在即视为旧后端模型」的安全变体（只删 `profile_ids` 对应文件），
  因重新引入 state 依赖被否决；纯用户目录误删风险由责任人明确接受。
- 批次目录名沿用 `catalog-custom-coexist`、分支名 `feat/catalog-custom-coexist-v2`，
  由责任人确认（2026-11-17，分支重落地、批次工作全新开始）。
