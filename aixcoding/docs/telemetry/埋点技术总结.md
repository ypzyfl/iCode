# iCode 数据上报埋点技术总结

> 归档范围：Zhoubin 于 2026-10-09 提交的 `6e336b6`、`e65c05b` 两次数据上报开发。本文依据当前源码和同目录设计、实现、调试记录整理；状态截至 2026-10-12。这里的“埋点”指 AIxCoding 定制遥测，不等同于 iCode 自带的 trajectory 分析或 OpenTelemetry 导出。

## 1. 需求与交付

该需求让 iCode 在模型调用、工具执行、AI 写文件和用户输入触发 skill 时，产生能被模型网关或 csas 后端关联的数据。核心交付是四类上报：

| 数据 | 触发点 | 通道 | 当前实现 |
|---|---|---|---|
| `llm-call` | 每次模型请求 | 随请求体 `telemetry` 发给模型网关 | `AixTelemetryMiddleware` 注入请求；响应中的工具调用登记关联 ID |
| `tool-detail` | 工具开始、结束 | csas `tool-detail/save`、`tool-detail/update` | 记录工具身份、状态、耗时、错误与写文件行数 |
| 输入触发 | 用户输入命中 slash skill 引用 | csas `tool-detail/save` | 单条 `funcType=0` 的 save，不发送 update |
| `ai-code` | `write_file`、`edit_file` 成功写入 | csas `ai-code/save` | 从文件快照生成代码 block，批量缓冲发送 |

定制源码位于 `src/chrys/aixcoding/`，定制测试位于 `aixcoding/tests/`，本目录保存设计和联调记录。上游接线主要在 LLM client 装配、EventBus 工具事件、引擎装配、输入解析和 ACP prompt。两个提交分别完成主体能力和工作区基准、csas 字段契约修正。

## 2. 数据流与关联模型

```text
模型请求 ── AixTelemetryMiddleware ── body.telemetry ──→ 模型网关
    │                  │
    │                  └─ 响应 function_call 的 provider_call_id
    │                     → (requestId, spanId) 进程内 registry
    ▼
工具 Start/Result ── EventBus ── subscriber ──┬─ tool-detail → 串行 HTTP 队列 → csas
                                                └─ ai-code → 批量缓冲 → 同一队列 → csas
slash skill 引用命中 ── record_skill_invocation ──→ tool-detail/save
ACP prompt _meta ──→ 渠道/功能入口；ACP prompt 响应 _meta ←── 最新关联 ID
```

`requestId` 是每次模型请求新生成的 UUID；同一次响应中的多个工具调用共享它。`spanId` 是同一 session、turn 的确定性根 UUID，工具上报通过 registry 取得与模型请求一致的值。registry 以 **provider 原始 call id** 为键，优先精确关联，找不到时回退到该 session 最新主调用；side call（如 judge、标题生成）虽注入 `eventSubType=system`，但不写 registry。`tool-detail.funcId` 也优先使用 provider call id，缺失时才用 Chrys 内部 call id。两种 call id 不可混为一个去重键。

LLM `telemetry` 放在 `extra_body` 中，由 wire 客户端合并到请求体顶层；它不经过 `aixcoding/http.py`，因此 csas mock 收不到。工具与代码上报走单个 `TelemetryHttpClient` worker 顺序 POST。`submit()` 只入队，失败记录日志，不阻断工具或模型流程。`BatchBuffer` 对 ai-code 达到 20 条或 10 秒时 flush，待发上限 500 条，超限丢最旧。独立上报在进程停机、取消 worker 或没有事件循环时存在未送达可能，不能把入队视为后端已落库。

## 3. 各埋点的字段与语义

### 3.1 llm-call

每次请求带 `requestId`、`sessionId`、`eventType=llm`、`eventSubType=agent|system`、渠道、插件版本、项目名，并在有值时带 `spanId` 与 git 信息。项目名和 git 信息以会话工作区 `SessionEnvironment.cwd` 为基准，未提供时回退进程 cwd。非流式响应直接提取 function call；流式响应在流终结的 result hook 提取，确保工具 Start 前 registry 已登记。网关的解析和入库回执不由 iCode 处理。

### 3.2 tool-detail 与输入触发

工具 Start 发送 save，随即发送 `codeStatus=3` 的 PENDING update；Result 再发送终态 update。`funcType` 为 MCP `1`、其余工具（含技能三工具）`3`；模型 `load_skill` 另补一条技能使用 save（`funcType=0`、`funcName=技能名`、saveOnly，2026-10-20 定稿）。终态 `codeStatus` 为成功 `1`、失败 `2`、用户拒绝 `4`；超时属于失败并附 `failureType=timeout`。终态还可附 `status`（成功 1、失败或拒绝 0）、耗时、起止时间、错误文本。`save.parentSpanId` 来自发起工具的那次 LLM 调用 span，与提问周期的根 `spanId` 分开。`executionDurationMs`、时间戳和 `failureType` 是 iCode 扩展字段，后端对超集字段的容忍度仍待确认。

默认 `value` 是普通工具调用原始参数的完整 JSON，与 pi-acp 一致；技能三工具固定上报 `skill_name`，沿用 2026-10-20 定稿口径；`parentSpanId` 和 `status` 是独立上报字段，不从参数中筛选；显式设置 `toolParamMode: whitelist` 时仅放行技能三工具（`load_skill`/`read_skill_resource`/`run_skill_script`）的 `skill_name`。路径类工具的 save 仍附 `fileName`：工作区内是含文件名的相对路径，工作区外保留原路径。Result 的 `metadata["file_snapshot"]` 实际是 `(before_text, after_text)` 元组；创建、删除按专门规则计数，修改使用 `difflib` 差异，输出 `originalLines`、`addedLines`、`deletedLines`。取消路径不发布 Result，故对应记录可能停在 PENDING，这是已接受的当前行为。

输入触发只在 slash skill 引用解析命中时上报一条 save，不在重试重放中重复记录。其 `funcName` 是 skill 名，`funcType=0`；本轮模型请求尚未发出，因此不填 `requestId`，只在取得关联时填 `spanId`。模型 `load_skill` 触发的技能使用 save 与之同构，但发生在请求之后：带 `requestId`/`spanId`、不带 `funcId`（工具调用 ID 不入技能使用记录，避免与 funcType=3 记录撞主键），skill_name 缺失时不补发。

### 3.3 ai-code

仅 `write_file`、`edit_file` 的成功 Result 且存在非空 `after_text` 和路径时上报；shell 隐式写入不在此范围。代码来源是 Result metadata 中的快照，不重新读取磁盘。一个文件生成一个 block，`snippet` 为写入后的全文，`rangeStart` 尝试定位旧文本中的新文本起点，无法定位时为 1。`filepath` 在工作区内转为相对路径。报文还含 `reportId`、`sourceType=edit`、`sessionId`，可带 request/span、git、渠道和功能入口信息。

审批状态由 `ApprovalModeUpdated`、`ApprovalRequest`、`ApprovalResponse` 事件追踪：manual 模式批准为 `codeStatus=5`，auto/judge/bypass 或无需审批为 `1`。拒绝时工具不执行，没有 ai-code 记录，`4` 体现在 tool-detail 终态。审批事件本身不区分用户与 judge 代答，目前以请求时 mode 近似判定；五态映射仍待产品和后端确认。

## 4. 配置与 ACP 接入

配置从 `<config_dir>/aixcoding.yaml` 和环境变量读取，首次读取后在进程内缓存。`AIXCODING_EXTENSION_PROFILE` 选择 `LOCAL|DEV|PROD`，`AIXCODING_EXTENSION_BASE_URL` 覆盖完整 base URL，`AIXCODING_TOKEN` 用作独立上报的 `token` 请求头，`AIXCODING_TELEMETRY_DISABLED=1` 关闭上报。YAML 还支持 `customServerUrl`、`userId`、`toolParamMode`、`telemetryEnabled`。当前 `userId` 仅有配置/provider 接口，真实登录数据源尚未接入。

ACP prompt 从 `_meta` 读取 `agent-studio.dev/ide-name`、`ide-version`、`function-name` 的 version 1 envelope，设置 desktop 渠道与功能入口；prompt 结束或取消响应可回传 `agent-studio.dev/telemetry`，包含最新主调用的 `requestId` 和可用的 `spanId`。渠道和功能入口当前为进程级最近值，多 ACP 客户端并发时会互相覆盖，需要未来按 session 隔离。

## 5. 验证证据与待办

2026-10-09 的联调记录显示：headless 原始 HTTP 日志确认 llm-call `telemetry` 已进入模型请求体，流式多次调用与并行工具的 request/span 关联成立；LOCAL profile 对接 mock 成功；tool-detail 的成功、异常、用户拒绝，以及 write_file 的 ai-code 已在 mock 入库核对。上述是既有记录，不代表本次文档整理重新跑过真实网关或 ACP 链路。

当前仍需验证或外部确认：

1. TUI/ACP 到真实网关查库、sub-agent 关联、ACP 审批及 `_meta` 客户端回传。
2. 工具超时、skill 输入触发、`edit_file`、manual 批准和 auto/judge 的真链路样本；故障注入下的端到端吞错。
3. 后端 `channelType` 枚举、`spanId` 口径、`codeStatus` 五态映射及扩展字段容忍度。
4. 登录来源接入、上游接线的哨兵测试，以及独立上报的停机排空策略。

排查方式：llm-call 看 session 下的 `llm_raw_http.jsonl`（启动前设置 `CHRYS_DEBUG_LLM_RAW_HTTP_LOG=1`；日志含完整敏感请求，勿外发）；独立上报可用 `AIXCODING_EXTENSION_PROFILE=LOCAL` 与 `uv run python aixcoding/telemetry-mock/server.py`，在 `/debug/view` 或 SQLite 中核对 save/update。定制测试需显式运行 `uv run --extra all pytest aixcoding/tests`，不会被上游默认 `testpaths` 或 Smart Test 自动收集。
