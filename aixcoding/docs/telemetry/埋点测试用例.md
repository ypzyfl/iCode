# iCode 数据上报埋点测试用例

> 适用范围：Zhoubin 在 `6e336b6`、`e65c05b` 中实现的 AIxCoding 定制上报。依据[埋点技术总结](埋点技术总结.md)和当前源码编写，2026-10-12。本文是测试设计与执行记录模板；“已有自动化”表示有对应测试代码，不表示本次已重新执行或真链路已验收。

## 1. 测试目标与判定口径

验证四类数据的触发、字段、关联、顺序与失败隔离：模型请求中的 `llm-call`，独立 HTTP 的 `tool-detail`、输入触发和 `ai-code`。验收分三层记录，不能互相替代：

| 层级 | 证据 | 边界 |
|---|---|---|
| 单元/组件 | `aixcoding/tests/` 的 pytest 断言 | 不证明真实模型网关或 csas 入库 |
| 本地链路 | 原始 HTTP 日志、telemetry-mock 的请求原文及 SQLite 记录 | mock 宽收未知字段，不证明生产后端兼容 |
| 外部联调 | 真实网关/csas 查库与 ACP 客户端收发记录 | 需记录环境、版本、sessionId、请求时间和脱敏证据 |

每个用例记录：执行日期、代码提交、运行环境、sessionId、关键 `requestId`/`spanId`/`funcId`、结果（通过/失败/阻塞/未执行）及证据位置。已有记录只可引用，不替代本轮执行结论。

## 2. 环境与测试数据

1. 安装项目依赖：`uv sync --extra all`。定制测试显式运行 `uv run --extra all pytest aixcoding/tests -m "not integration and not gc_calibration"`；默认 pytest `testpaths` 与 Smart Test 不自动收集该目录。
2. 本地 csas mock：`uv run python aixcoding/telemetry-mock/server.py --db /tmp/icode-telemetry-test.db`，启动后访问 `http://127.0.0.1:4321/debug/view`；测试进程启动前设置 `AIXCODING_EXTENSION_PROFILE=LOCAL`。使用专门测试 session，必要时 `POST /debug/clear` 清空数据。
3. 模型请求体：启动 iCode 前设置 `CHRYS_DEBUG_LLM_RAW_HTTP_LOG=1`，在 session 目录检查 `llm_raw_http.jsonl` 中 `event=request` 的 `request.body.json.telemetry`。原始日志可能含 API key、完整 prompt 和工具参数，只留在受控环境，分享证据前脱敏。
4. 准备一个 git 工作区和隔离的临时文件目录。建议文件样本：新建 `a.txt`（3 行）、编辑成 4 行（增 2 删 1）、删除样本；同时准备工作区外路径以检查绝对路径回退。写类真链路用例只能写测试文件。
5. 手工审批用例使用 TUI 或 ACP 的 manual 模式；`icode run` 是 BYPASS，不能用于验证人工批准/拒绝。ACP `_meta` 用例需要能够发送 envelope 并读取 prompt 响应的客户端。

mock 观测接口：`GET /debug/reports?interface=tool-detail/save&sessionId=<id>` 等；`interface` 可换 `tool-detail/update`、`ai-code/save`、`rejected`，或用 `GET /debug/dump`。记录原始 `body_json`，不要只看页面提取列。llm-call 不经过该 mock。

| A08 | 使 provider call id 缺失或 registry 精确键未命中，触发工具上报 | `funcId` 缺失 provider id 时回退内部 call id；关联回退 session 最新主调用，均不得异常中断 | `test_llm_telemetry.py`、`test_tool_detail.py` |

## 4. 执行顺序与验收记录

建议先跑定制 pytest，再做 LOCAL mock 的 B01/B04/B06/B08/C01，随后做流式关联、ACP 与真实后端。`ai-code` 有 10 秒缓冲，查询前应等待发送或显式排空测试中的 buffer；不要在请求刚返回时立即判定漏报。每轮独立上报用唯一 sessionId，避免 mock 裸插入的旧记录干扰。
