### C1【PII 盲区】loader/startup 主通道文案的 `{exc}` 可变字段未纳入 F1 修复与 PII 哨兵

- 依据：`src/chrys/service/aixcoding/config/loader.py:148-150`（`except (OSError, tomllib.TOMLDecodeError, UnicodeDecodeError) as exc: _warn(f"配置文件无法解析（{exc}），已回退全部默认。")` → `_warn` 内 `_log.warning("%s", message)` 进主通道）与 `src/chrys/app/aixcoding/startup/__init__.py:42`（`message = f"启动任务 {task.__name__} 失败（{exc}）；已跳过。"` → `_log.warning` 进主通道）。**OSError 的 str 携带绝对路径**（如 `PermissionError: [Errno 13] Permission denied: 'C:\Users\<name>\...aixcoding.toml'`）、`_ensure_file_sink` 的文件系统异常同理——`{exc}` 原样进主卷即泄漏用户名。F1 修复处理了 environment `origin`（字面化）与 guard 备份路径（相对形）两处，但 `{exc}` 文本字段是同类泄漏的残留面。
- 测试侧：`test_config_warn_triple_channel` 的 `cannot-parse` 场景注入语法坏 toml（`TOMLDecodeError` str 无路径）；`test_startup_task_failure_triple_channel` 注入 `RuntimeError("wiring failed")` 固定文本——**注入异常均无路径**，`test_main_channel_pii_sentinel` 的 `_looks_like_path`（盘符//Users//home/）只覆盖 guard 重置 + environment 两个场景（`len(public_messages) == 2`），`{exc}` 注入路径的异常链未过哨兵。
- 可能后果：配置文件权限损坏 / sink 建立失败的罕见场景下，主卷 WARNING 携带带用户名的绝对路径——与 F1 当初要防的"用户把日志贴工单泄漏路径"同类。
- 影响面：仅日志文案（宿主功能零影响）。
- 冲突点：requirements 验收 7「主通道新增文案 PII 哨兵：不含 ehr、完整 URL、异常栈」+ self-review「F1 复审通过、blocker 清零」——哨兵对 `{exc}` 携带路径的注入路径不设防。
- 来源：本批引入（F1 修复不完整的边角）。
