## 背景

产品事实：AIxCoding CLI/TUI 只需支持中文（ADR-0005 确认意见——2026-10-23 与吴正老师确认，
无需支持英文）。ADR-0005（2026-10-23）就"tui 文案"决策：中文常量、不纳入 i18n、**不引入
`msg()`**，适用范围限于 tui 新增界面。

2026-10-27 tui 批次 design（决策点 D2）暴露两件事：

1. 上游 `SlashCommandDef.description` / `man_page` 为 `MessageRef` 强类型
   （`src/chrys/app/tui/widgets/chrome/commands.py:86,95`，无 str 分支），命令注册处
   **绕不开 `msg()`**——"不引入 msg()"字面不可全量执行，只能"借壳"：`msg(key,
   fallback="中文").bind()`（zh 查表命中条目、en 回退 fallback，两界面均显示中文，
   效果与纯常量一致）。
2. 负责人裁定将口径从"tui 文案"泛化为**全定制面 i18n 原则**，并叠加例外判定程序与
   最少上游改动的耦合约束（原话："在不破坏原有的'能不改上游代码就不改，能少改上游代码
   就少改'原则的基础上，对于 i18n，原则上定制化部分只支持中文，如果有特殊情况必须中英文
   或者中英文的收益明显时，才考虑中英文，同时，需要告知理由"）。

**什么变了**（对照 ADR-0005）：范围 tui 文案 → 定制面全部用户可见文案；"不引入 `msg()`"
→ "上游强类型处 `msg` 中文 fallback 借壳合法"；新增例外判定程序与"不扩大上游改动"耦合约束；
**重评期限条款承接不变**：产品需要英文界面时重评（沿用 ADR-0005 期限，触发时按第 3 条例外程序具名展开）。

## 决策

**定制面用户可见文案以中文单语为纲：默认纯中文常量；上游强类型处允许 `msg(key,
fallback="中文").bind()` 借壳——借壳条目随上游 i18n 流水线登记（pot + po 中文条目 +
oracle），不引入英文翻译；例外（必须双语或双语收益明显）须在所属批次 design 中具名并给出理由。**

细则：

1. **默认载体** = 纯中文常量（含 f-string 拼接），不引入 `msg()`——无上游类型约束处一律如此。
2. **借壳形态** = `msg(key, fallback="中文").bind()`（`msg()` 返回 `MessageDef`，注册表等
   `MessageRef` 消费方必须 `.bind()`，照抄 `msg(...)` 裸调用即 ty 红 + 运行时崩），仅当上游
   API 强类型要求时使用；fallback 写英文即视为双语诉求，必须走第 3 条例外程序，否则违规；
   借壳 key 统一 `aixcoding.*` 前缀（满足上游 key 语法，catalog 中可辨识）。
   **登记义务**（上游 i18n 流水线为 pot/po/oracle 三方 key 集合强一致门禁，2026-10-27
   peer review 破坏性实验实测，无法绕过）：① extract 进 `locales/chrys.pot`；②
   **po 登记中文条目**（`msgstr` = 中文文案，由 fallback 复制即得——这不是英文翻译）；
   ③ 上游 oracle 登记——**两处动作缺一不可**（上游约定 "the oracle test pins both the
   id set and its size"，`_catalog_oracle_ids.py:16-17`）：`_catalog_oracle_ids.py`
   id 集合 +1 行/条目 **且** `test_catalog_oracle.py` 的 size 断言同步 +1（R2 报批）。
   oracle 对 po 集合与"有可见翻译"集合做双等断言，`msgstr` 非空缺一不可。zh 与 en 界面均显示
   中文，实际效果 = 中文单语。改文案义务 = 同步 fallback 与 po `msgstr` + extract + update。
3. **例外程序**：某文案面若必须中英双语、或双语收益明显 → 所属批次 design 单列文案决策节：
   具名例外面 + 理由 + 上游 locales 接触面增量；负责人签认 design 即为准入。
   "收益明显"的判定：须以**可论证的英文使用场景**为前提（缺场景即不成立），批次作者首提、
   负责人签认兜底。
4. **耦合约束**：本决策不得以扩大上游改动为代价——借壳的登记义务（pot/po/oracle 三点）
   为强类型约束下的被迫下限；超出下限的上游接触（英文翻译条目、放宽 oracle 断言、改流水线
   机制等）按第 3 条例外程序具名（与 R1"最少最集中"、R2 报批联动）。
5. **上游文件内嵌的定制文案**（命令注册、通知流等）同样适用本决策；进入上游 i18n 测试射程
   的条目按实际红绿处理并在所属批次 design 假设节钉死（首个适用实例：tui 批次，随批次入库）。

## 理由

1. **双语收益不存在于真实场景**：`/language en` 已被产品决策否定；zh 界面下借壳与纯常量
   用户可见效果完全相同。
2. **维护义务**（2026-10-27 实测修正）：英文双语文案 = 改文案须 extract/update 两步 +
   英文 fallback 与 zh 翻译两处文案维护；借壳条目 = extract/update 两步 + po `msgstr`
   随 fallback 复制同步（无英文写作）；纯常量 = 零流水线义务。借壳的优势是**免除英文维护**，
   不是零义务。
3. **升级冲突面**（2026-10-27 实测修正）：借壳条目随 pot/po/oracle 三文件漂移平移
   （每条目约 po +6 行 + oracle +1 行），相比英文双语省去翻译写作；相比纯常量的零接触，
   是强类型约束下的被迫代价。
4. **被否决备选的死因**（R8 记录义务）：
   - *全量英文 fallback + zh PO*（0.28 旧形态）：收益仅存于产品已否定的 en 场景，代价永久
     （英文+翻译双维护 + 漂移平移）——tui 批次 D2 对比后否决；
   - *直接构造 `MessageRef` 实例绕过 `msg()` 清零 catalog 条目*：**可行但被否决**——实测
     私有 `_CONSTRUCTION_TOKEN`（单下划线哨兵，非 name-mangling）可直接传入构造，绕过
     `msg()` 后 extract 不收录、catalog 零条目；但这是依赖上游非公开实现（单下划线无 API
     承诺，升级易碎；正命中 ADR 判定④），为省每条目 ~7 行流水线产物不值得冒险；
   - *改上游类型签名（`SlashCommandDef.description`/`man_page` 放宽为 `str | MessageRef`）
     以纯常量直传*：为定制需求放宽上游通用类型，调用方与渲染处连带分支，R1 升级冲突面最大
     ——上游强类型（"Locale-neutral"）系有意设计，不为其破例；
   - *维持 ADR-0005 原文不动*：字面"不引入 msg()"与强类型现实冲突，每个新批次都要重新
     口头解释，决策债滚动累积。
