## 背景

定制代码的依赖策略此前仅规范 §9 一句弱条款（"说明理由与许可证兼容性，并锁定版本"）——只有说明义务，没有停等点与批准动作，AI 或成员可自行引入依赖。同时存在管辖缺口：运行时依赖必改 `pyproject.toml`，形式上落入 R2，但 R2 审的是改动范围（哪个文件、几行），不审"这个依赖该不该引入"；开发资产依赖（`aixcoding/tests/`、`aixcoding/tools/` 用）不改任何上游文件，此前完全无管控。

本仓特有三个风险维度：① 供应链——新依赖即新攻击面与传递依赖树；② 升级摩擦——新依赖写入 `uv.lock` 即扩大与上游 lock 的冲突面、升级时版本约束可能不兼容，与规范核心目标（最小化升级成本）直接冲突；③ 离线打包——构建走下载物永久缓存方案，新依赖扩大离线构建的下载物清单与复杂度。

## 决策

*（本文为决策时点快照；现行规则以 DEVELOPMENT.md R11 为准。）*

新增硬规则 R11：定制代码（`src/chrys/aixcoding/` 与根 `aixcoding/` 全部资产）新增第三方依赖——运行时或开发用——**默认拒绝**，引入前须报批。申请五项：① 现有手段逐项排除（标准库 / 已有依赖 / 上游已有依赖）；② 许可证兼容性；③ 供应链评估（维护活跃度、使用量、传递依赖树）；④ 锁定版本；⑤ 对 uv.lock 冲突面与离线打包的影响。审批留痕于 design.md 头部审批人/审批日期字段（仅依赖引入时必填；经审批人同意后由责任人代填，AI 不得代填）；依赖引入通常命中 ADR 判定②（撤销代价高），应出 ADR。跟随上游升级带来的依赖变更（上游自身的增删）不在此列；mock 专区维持 stdlib-only 更强约束。

## 理由

1. **R11 与 R2 互补而非重复**：R2 管"改上游文件"这个动作，R11 管"引入依赖"这个决策——供应链、许可证、维护活跃度、升级摩擦均不在 R2 评审射程内；且 R11 补上开发依赖这一 R2 触及不到的空白。
2. **撤销代价高**：依赖一旦被业务代码使用，移除成本随使用面单调增长，且传递依赖可能被间接锚定——这正是 ADR 判定②，故每次引入也应出 ADR 留决策档。
3. **审批落盘复用既有机制**：design.md 签认 + ADR，不新增文档形态；引入依赖从此成为"方案未签，不动代码"铁律家族的显式停等点。

## 否决的备选

- **维持 §9 弱条款（只说明、不审批）**：无停等点即无审批实质；纯说明义务无验证机制，等于自律。开发依赖连说明义务都覆盖不到（条文挂在"定制代码自身约束"节，语境默认运行时）。
- **完全并入 R2（依赖必改 pyproject 所以已被覆盖）**：覆盖不了开发依赖；且 R2 的报批粒度（文件/行数）承载不了供应链与许可证的决策维度。
- **一律禁止新增依赖（硬上限）**：过刚——真实必要场景（加密、协议库等自研不现实者）无法满足，逼出的绕行（vendor 复制源码进定制目录）供应链面更糟且失去版本治理。
- **机器门禁自动拒绝（CI 扫依赖 diff 即红）**：依赖 diff 的检测可机器化，但"该不该引入"是人的决策——机器守门不裁决；提示性扫描登记为后续可选增强，不作当前依赖。

## 后果

- 引入第三方依赖从此是显式停等点：方案阶段报批（五项申请），签认后实施；
- 审批记录落盘于功能文档目录的 design.md 签认与对应 ADR，不以聊天记录为凭（同 R2）；
- §9 原弱条款改写为指向 R11，规范唯一权威维护点在 R11；
- 可选后续增强：CI 对 `uv.lock` / `pyproject.toml` diff 的提示性扫描（发现未报批引入），登记备查不预设。
