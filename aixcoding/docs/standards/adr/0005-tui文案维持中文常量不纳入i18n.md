# ADR-0005：tui 文案维持中文常量，不纳入 i18n

- 责任人：周彬

## 背景

上游 i18n 流水线：代码中 `msg("English key")` → `scripts/i18n.py extract`（AST 扫描 `src/chrys` 下 `msg()` 调用，SOURCE_ROOT 硬编码为 `src/chrys`）→ `locales/chrys.pot` → 人工翻译 zh-Hans PO → 编译 `.mo` 随 wheel 分发 → 运行时按语言查表回退原文。CI 有 `check` 门禁：源码加了 `msg()` 而 catalog 未刷新即红。

事实核查（`aixcoding/tui/login.py`）：登录对话框文案是裸常量、直接写中文、**没有用 `msg()`**——`_TITLE = "AIxCoding 登录"`、`_OPEN_BUTTON = "在浏览器中继续"` 等。历史上放根目录时（提取器射程外）**没资格**用 `msg()`，"直接中文常量"是被迫妥协而非设计选择。迁入 `src/chrys/aixcoding/tui/` 后进入射程，**获得**了使用 `msg()` 的资格——注意：提取器只认 `msg()` 调用，裸常量迁入不会自动进 catalog、check 不会红。真正的决策是：要不要把资格用起来。

## 决策

维持中文常量，不改用 `msg()`；在 DIRECTORY.md §8 登记为例外（期限：产品需要英文界面时重评）。

## 理由

1. **收益趋零**：AIxCoding 是内部产品，用户基本中文；`msg()` 换来的"语言切换能力"无人使用。
2. **成本是永久义务**：改用 `msg()` 后每次改文案都必须同步 extract/update/translate/compile，且被 CI `check` 门禁强制——一次性工作换来持续摩擦。
3. **迁移 churn 是纯亏损**：现有中文常量含 f-string 失败消息（`_show_failure`），转 msg() 占位符模式改动不小。

（注：本 ADR 立场经历了反转——最初倾向"纳入多语言"，读完 `login.py` 确认文案已是精心编写的中文常量、且产品无多语言需求后改为维持现状。记录此过程以防反复。）

## 否决的备选

- **改用 `msg()` 纳入多语言体系**（英文 key + zh-Hans 翻译）：见理由 1–3，被否决；留活口——若产品未来需要英文界面，整体转 `msg()` 并补 catalog。

## 后果

- 迁移时唯一连带：ruff per-file-ignores 的 `"aixcoding/tui/*" = RUF001`（中文全角标点在英文语境规则的豁免）改路径为 `"src/chrys/aixcoding/tui/*"`；
- i18n `check` 应无任何变化（无新增 `msg()` 定义）——重建验收项之一；
- 新增 tui 定制界面时沿用本决策：文案直接中文常量，不引入 `msg()`。（现行适用范围以 DIRECTORY.md §8 例外表为准；本文为决策时点快照。）
