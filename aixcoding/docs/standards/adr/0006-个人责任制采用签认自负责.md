## 背景

AI 辅助开发（AI 起草文档与代码）下需要保证人负责制：AI 不能承担决策责任，且要防"橡皮图章"（人扫一眼点头，形式有批准、实质无思考）。组织实际：**一人一功能**——开发者借助 AI 生成文档与代码，自己审阅迭代，最终自己确认；PR 由另一人 peer review。

## 决策

*（本文为决策时点快照；现行规则以 DEVELOPMENT.md R10 与 §4.1 为准。）*

采用**责任人签认**（self-attestation）：每个任务/功能有唯一责任人，**需签认的文档收敛为两类**——`design.md` 与 ADR（决策档：承载 R2 批准，**仅 R2 清单变更须重签**）与 `self-review.md`（记录档：双 AI 自审产出，签一次追加不重签）；其余功能文档（requirements / test-plan / plan / verification）为活文档不签认。签认字段组（`责任人 / 状态 / 确认日期 / 确认意见[可选]`），签认 = 责任人**本人**编辑字段并提交，AI 不得代填。配套：`check_docs.py` 校验 + `git blame` 抽查；peer review 是质量互助但不转移责任；证据链三重留痕（签认字段 + blame + PR review 记录）。

## 理由

1. 责任锚点匹配组织实际：自负责模式下，"人对批了什么负责"的载体就是本人签字，无需第三方权威。
2. **git 提交身份 = 责任身份**：blame 校验签字行的实际修改者与字段责任人一致，防跨人代签；防篡改（签认后修改暴露于 blame 与重签检测）。
3. 最小人动作集（可落地性）：签认 = 改状态、填日期，一分钟内；起草、誊录、校验、台账全部由 AI 与脚本承担。流程的存活依赖人的负担趋近于零。
4. 诚实的技术边界被接受：防不住"本人不看就签"（技术上不可区分）——以抽查与追责威慑兜底，不追求机器证明人思考过。

（演进注记 2026-10-23：R11 新增第三方依赖的批准增设审批人留痕——design.md 头部"审批人/审批日期"字段（仅依赖引入时必填），流程为申请人找审批人过目、同意后由申请人本人代填（AI 不得代填）。自负责制不变：设计内容与 R2 上游改动仍以责任人签认自负责；授权留痕仅限依赖引入，谎报与"不看就签"同属诚实边界，以抽查与追责兜底。依赖清单变更须重新过审批人。）

## 否决的备选

- **lead 集中批准**（CODEOWNERS + 分支保护 + 独立批准 PR + 批准意见誊录 + "批准意见"强制非空）：与"一人一功能、自审自签"的组织实际不符；lead 成为所有文档 PR 的瓶颈；流程摩擦大难落地。演化注记：本决策经历了从该方案到签认自负责的完整反转，记录于此防止走回头路。
- **"确认声明"固定句**（"我已审阅本文档全部内容，对其内容与后果负责"）：签认的责任效果来自 git 记录与字段事实，声明句只是仪式感，而仪式感即压迫感——删除。
- **"提案人"署名字段**（"AI 起草 / 人复核"逐份标注）：默认工作模式即 AI 起草、人复核，无需逐份声明；起草者信息 git 历史天然有。
- **GitHub PR approve 作为批准锚**（平台记录不可伪造）：保留为 peer review 的既有动作，但不再作为责任锚——签认 + blame 已足够且更简。

## 后果

- 规范 R10、§4.1 责任人检查点、`design.md`/ADR/`self-review.md` 模板头部的签认字段组、`check_docs.py` 校验（本地已可用，CI 随 aixcoding-tests.yml 挂接）；
- **签认范围演进注记（2026-10-23）**：初版要求全部功能文档签认；因需求频繁变更导致重签负担，收敛为"design/ADR + self-review"两类——活文档的日常变更由 git 留痕覆盖，人的签认集中在"批什么（design）"与"产出了什么（self-review）"两个关键点。
- R2（上游改动审批）的批准记录落盘于设计文档签认与确认意见，不再依赖口头/聊天记录；
- 抽查操作：字段 → blame → PR review 三步对账。
