# 评审怎么做（PEER-REVIEW HOWTO）

> **给谁用**：评审人（他人的 PR）。打开 PR 时打开本文照做。
> **与自审的关系**：作者已按 `SELF-REVIEW-HOWTO.md` 完成双 AI 自审并提交 `self-review.md`（已签认）；你的职责是**裁决**。**review 是质量互助，不转移责任**（R10）。
> **微改动 PR**（§6 豁免）：先核豁免资格——§6 三条件对照 diff（零上游文件 / 不触发 ADR / 定制目录内约百行），超范围即 request changes 转完整管线；然后方案速评（大方向表态：改法对不对，一句话结论 + 理由；直觉有更好做法必须写出）+ 缺陷模式抽查 + 验证输出必看，通常几分钟；**含 madr/ 条目 diff 时 §三 ⑤ 必做**（档位 + 详证 / append-only 守护）。

## 一、流程（四步）

```
① 读 PR 描述：变更导览是你的时间分配表；确认 self-review.md 已提交且已签认
   （缺失或未签认 = 流程违规，直接 request changes 要求补，不进入评审）
②（建议）换 AI：用与作者不同的 AI 跑一遍 §二 各项检查
③ 人裁决：§三 的核心动作，守住各项 100% 硬标准
④ 留痕：裁决逐条写在 PR 评论（格式见 §四），approve / request changes
```

## 二、评审人 AI 指令模板（建议使用）

```
你是独立评审 AI。我在评审一个 PR，请独立执行以下三组检查（结果可能与作者自审冲突，冲突本身就是发现；次序即优先级——先核改动本身，再扫缺陷，最后对合规）。

评审背景（规范摘要，已内嵌无需另读文件；全文见 aixcoding/docs/standards/DEVELOPMENT.md）：
- R1 非侵入优先，必改上游时少而集中（迁移批次含逐行归属细则，见 DEVELOPMENT.md R1）；R2 上游改动必须先获批；R3 获批改动带 AIxCoding 标记注释
- R4 新增文件只允许落 aixcoding 目录（产品代码按 tier 落位 `src/chrys/{tier}/aixcoding/`，ADR-0011）；R9 档位=能容纳全部依赖的最低档，放错层 test_layering 即红
- R5 最小变更；R7 验证须附真实命令与输出；R11 新增第三方依赖默认拒绝、须审批
- R12 迁移批次方案重审：旧实现只是内容索引——对照目标基线同类机制现状同构跟随（不做形态平移），design 必含"是否有更优方案"专题
- R13 豁免须理由与批准：豁免（架构登记/noqa/skip/CI 跳过/closure 存量缺件新增或扩大等）是穷尽正当路径后的设计后备——新增须责任人批准、就地注释理由与批准指向，AI 不得自行添加；closure 清单新增/扩大另须签认 ADR（ADR-0024）
- ADR-0012：开工判定单协议（§4.2——任务路由与豁免由责任人裁决，免判定清单外 AI 不得自判）+ git 写操作逐条授权（§4.1 铁律④）；diff 超出已签 design 范围且不属免判定清单（§4.2）即流程违规
1. 改动本身独立复核（技术评审，与 SELF-REVIEW-HOWTO §二 第一阶段（T1-T4）同构——你是独立第二道，
   不是重复自审全流程；与自审结论冲突 = blocker 级候选；要点如下，全文见该文件）：
   - T1 方向审视：方案是不是在解决动机本身（答非所问？反查 requirements 目标与验收标准
     有无漏做？）——大方向表态 + 理由，不采信 design 的自我论证
   - T2 关键决策权衡：每个决策用什么代价换什么收益、什么条件下反转；值/阈值有依据吗；
     被放弃做法你重新评估过吗；直觉有更好做法必须写出（收尾显式回答"未发现更优做法"）
   - T3 实现深读：读懂完整逻辑再下结论（不是 diff 碎片，含下游调用点核对）；实现-方案保真
     （统一模式有没有各写各的）；该复用的公共设施复用了吗；多平台/多路径分支对称（不对称
     须有理由）；测试更新是如实锁定新行为还是放松迁就实现；文档与实现一致
   - T4 技术风险：热路径与量（日志/上报频次）、上游升级冲突面、可维护性
   - 临时项三件套：写死/绕行/降级类改动须有期限、恢复路径、副作用说明（缺一样 = 候选
     finding）；副作用（改动波及谁）已列且有接受记录
2. 缺陷模式：
   - 幻觉 API 验证：对 diff 新增 import 的每个符号查证定义存在与签名正确，输出证据（定义文件:行）
   - 缺陷模式扫描：按（边界/异常/并发）扫 diff，输出候选 findings——只列候选与依据，
     不下结论（裁决我来做）
3. 合规比对：
   - R2/R11 比对：列出 git diff 中所有上游文件与 pyproject.toml/uv.lock/新 import 的第三方变化，
     与 docs/<feature>/design.md 的 R2 清单和依赖申请节逐项对名，输出"清单内/清单外"标注
   - closure 对账：核对 check_docs.py --closure 结果与 closure-exemptions.toml diff；豁免只能精确减少，
     新增/扩大须指向已签 ADR，stale 项或新增缺件批次目录均输出候选 blocker
   - madr/ 条目核对（diff 含 madr/ 新增或修改时）：新增条目核对档位恰当（未命中 ADR checklist？）
     + 详证载体支撑（决定人与决定内容被本 PR 描述/所指向载体严格支撑）；修改既有条目
     确认确属 typo/链接/格式等非决策性修正（append-only 守护）
```

## 三、核心动作与硬标准

| 动作 | 具体做法 | 硬标准 |
|---|---|---|
| **① 上游接触面逐行** | 逐行读，每处改动问四个问题：**必要吗**（不改上游能否实现，R1 重问）？**最小吗**（行数能否更少、能否更集中）？带 `AIxCoding` 标记吗？与 R2 清单一致吗？ | **100% 过目** |
| **② blocker 裁决** | 作者 self-review 的 blocker + 自己/自己 AI 发现的 blocker，逐条 confirm / reject | **100% 裁决且留痕于 PR** |
| **③ 方案与实现复核** | 读 PR 变更导览的**核心区域**，按 SELF-REVIEW-HOWTO §二第一阶段（T1-T4）做技术复核：大方向是否解决动机本身（有无答非所问）、关键决策权衡是否站得住（值/阈值有无依据）、实现是否保真（统一模式有没有各写各的、该复用有没有复用）、临时项三件（期限/恢复路径/副作用说明）、跨平台/跨路径分支是否对称、文档（docstring/批次文档/使用手册）与实现是否一致；对照 self-review.md「方案与实现评估」行 confirm / reject——**只写"方案与动机对应"类空话的评估 = 拒回补** | 核心区 **100% 过目**（纯定制 PR 尤必——它没有上游 diff 替你分配时间） |
| **④ 证据抽查** | verification.md 抽一条可复跑的命令复跑；验收标准与测试对应关系扫一眼 | 抽查（不再要求 100% 对应） |
| **⑤ madr/ 条目核对**（diff 含 madr/ 新增**或修改**时） | **新增条目**：档位恰当（未命中 ADR checklist？命中①"认真权衡过备选"即该出 ADR）+ 详证载体支撑（决定人与决定内容被本 PR 描述/所指向载体严格支撑）；**修改既有条目**：确认确属 typo/链接/格式等非决策性修正（append-only 守护） | **100% 过目**（有 madr/ diff 时；微改动 PR 同样适用） |

其余（纯定制目录代码的**缺陷模式**逐行检查等）**风险导向抽查，不要求逐行**——注意力与升级摩擦风险对齐；§三③ 的方案与实现复核不属"其余"，见 §五。

## 四、裁决评论写法（示例）

confirm（要求处置，附证据——让作者不用复查就知道怎么改）：
```
confirm blocker-2：幻觉 API 属实——chrys.kernel.middleware.ChatContext 无 timeout_ms 参数
（定义见 kernel/middleware.py:41），请改用 set_timeout 或调整调用。
```

reject（否决 finding，附理由——不许随手 dismiss）：
```
reject finding-3："过度工程"不成立——该防御分支对应 verification.md 2026-10-20 记录的
Windows 实测故障（IOCP 取消超时），保留。
```

## 五、时间预算

- **合规比对**（上游逐行、R2/closure）的时长随**上游接触面行数**走——上游 diff 大的 PR 不设上限但逐行；
- **方案与实现复核**（§三③）的时长随**改动本身的风险**走——与是否上游无关，纯定制 PR 同样全份适用；
- 纯定制目录的中小 PR：各项动作应在 ~15 分钟内；
- 自查信号：**合规比对**之外，如果你在纯定制代码上逐行纠风格，说明注意力错配了——方案/实现/文档一致性问题不算错配。

## 六、FAQ

**Q1：我没有个人 AI 工具，怎么办？** AI 各项检查是**建议非强制**——没有就人工做两项关键的：R2 比对肉眼对表、幻觉 API 手动跑 `python -c "from x import y"`；缺陷模式扫描降为风险导向抽查。§三 的人的硬标准（逐行 / 裁决 / 方案复核 / 抽查 / madr 核对）不变。

**Q2：我的 AI 与作者的两个 AI 结论都冲突？** 冲突本身就是 blocker 级 finding——先查三方证据链再裁决。

**Q3：作者没交 self-review.md 或未签认？** 流程违规——request changes 要求补，不进入评审（§4.2 步骤 5 是强制项）。

**Q4：微改动 PR 评什么？** 先核豁免资格（§6 三条件对照 diff——零上游文件 / 不触发 ADR / 定制目录内约百行；超范围 = request changes 转完整管线）；然后方案速评（大方向表态：改法对不对，一句话结论 + 理由；直觉有更好做法必须写出）+ PR 描述里的双 AI 精简评审结论 + 验证输出必看；含 madr/ 条目 diff 时 §三 ⑤ 必做；几分钟内完成。
