# 评审怎么做（PEER-REVIEW HOWTO）

> **给谁用**：评审人（他人的 PR）。打开 PR 时打开本文照做。
> **与自审的关系**：作者已按 `SELF-REVIEW-HOWTO.md` 完成双 AI 自审并提交 `self-review.md`（已签认）；你的职责是**裁决**。**review 是质量互助，不转移责任**（R10）。
> **微改动 PR**（§6 豁免）：只做缺陷模式抽查 + 验证输出必看，通常几分钟。

## 一、流程（四步）

```
① 读 PR 描述：变更导览是你的时间分配表；确认 self-review.md 已提交且已签认
   （缺失或未签认 = 流程违规，直接 request changes 要求补，不进入评审）
②（建议）换 AI：用与作者不同的 AI 跑一遍 §二 三项交叉
③ 人裁决：§三 的三个核心动作，守住两个 100%
④ 留痕：裁决逐条写在 PR 评论（格式见 §四），approve / request changes
```

## 二、评审人 AI 指令模板（建议使用）

```
你是独立评审 AI。我在评审一个 PR，请独立执行三项检查（结果可能与作者自审冲突，冲突本身就是发现）。

评审背景（规范摘要，已内嵌无需另读文件；全文见 aixcoding/docs/standards/DEVELOPMENT.md）：
- R1 非侵入优先，必改上游时少而集中（迁移批次含逐行归属细则，见 DEVELOPMENT.md R1）；R2 上游改动必须先获批；R3 获批改动带 AIxCoding 标记注释
- R4 新增文件只允许落 aixcoding 目录（产品代码按 tier 落位 `src/chrys/{tier}/aixcoding/`，ADR-0011）；R9 档位=能容纳全部依赖的最低档，放错层 test_layering 即红
- R5 最小变更；R7 验证须附真实命令与输出；R11 新增第三方依赖默认拒绝、须审批
- R12 迁移批次方案重审：旧实现只是内容索引——对照目标基线同类机制现状同构跟随（不做形态平移），design 必含"是否有更优方案"专题
- R13 豁免须理由与批准：豁免（架构登记/noqa/skip/CI 跳过等）是穷尽正当路径后的设计后备——新增须责任人批准、就地注释理由与批准指向，AI 不得自行添加
- ADR-0012：开工判定单协议（§4.2——任务路由与豁免由责任人裁决，免判定清单外 AI 不得自判）+ git 写操作逐条授权（§4.1 铁律④）；diff 超出已签 design 范围且不属免判定清单（§4.2）即流程违规
1. R2/R11 比对：列出 git diff 中所有上游文件与 pyproject.toml/uv.lock/新 import 的第三方变化，
   与 docs/<feature>/design.md 的 R2 清单和依赖申请节逐项对名，输出"清单内/清单外"标注
2. 幻觉 API 验证：对 diff 新增 import 的每个符号查证定义存在与签名正确，输出证据（定义文件:行）
3. 缺陷模式扫描：按（边界/异常/并发）扫 diff，输出候选 findings——只列候选与依据，
   不下结论（裁决我来做）
```

## 三、核心动作与硬标准

| 动作 | 具体做法 | 硬标准 |
|---|---|---|
| **① 上游接触面逐行** | 逐行读，每处改动问四个问题：**必要吗**（不改上游能否实现，R1 重问）？**最小吗**（行数能否更少、能否更集中）？带 `AIxCoding` 标记吗？与 R2 清单一致吗？ | **100% 过目** |
| **② blocker 裁决** | 作者 self-review 的 blocker + 自己/自己 AI 发现的 blocker，逐条 confirm / reject | **100% 裁决且留痕于 PR** |
| **③ 证据抽查** | verification.md 抽一条可复跑的命令复跑；验收标准与测试对应关系扫一眼 | 抽查（不再要求 100% 对应） |

其余（纯定制目录代码的缺陷模式检查等）**风险导向抽查，不要求逐行**——注意力与升级摩擦风险对齐。

## 四、裁决评论写法（示例）

confirm（要求处置，附证据——让作者不用复查就知道怎么改）：
```
confirm blocker-2：幻觉 API 属实——chrys.kernel.middleware.ChatContext 无 timeout_ms 参数
（定义见 kernel/middleware.py:41），请改用 set_timeout 或调整调用。
```

reject（否决 finding，附理由——不许随手 dismiss）：
```
reject finding-3："过度工程"不成立——该防御分支对应 verification.md 2026-10-20 记录的
Windows 实测故障（IOCP 取消超时），保留。
```

## 五、时间预算

- 评审时长的主要变量是**上游接触面行数**——导览的"核心区域"就是你的时间分配表；
- 纯定制目录的中小 PR：三动作应在 ~15 分钟内；上游接触面大的 PR 不设上限但逐行；
- 自查信号：如果你在纯定制代码上花的时间超过上游 diff，说明注意力错配了。

## 六、FAQ

**Q1：我没有个人 AI 工具，怎么办？** AI 三项交叉是**建议非强制**——没有就人工做两项关键的：R2 比对肉眼对表、幻觉 API 手动跑 `python -c "from x import y"`；缺陷模式扫描降为风险导向抽查。§三 的人的硬标准（逐行 / 裁决 / 抽查）不变。

**Q2：我的 AI 与作者的两个 AI 结论都冲突？** 冲突本身就是 blocker 级 finding——先查三方证据链再裁决。

**Q3：作者没交 self-review.md 或未签认？** 流程违规——request changes 要求补，不进入评审（§4.2 步骤 5 是强制项）。

**Q4：微改动 PR 评什么？** PR 描述里的双 AI 精简评审结论 + 验证输出必看；几分钟内完成。
