# 团队成员指南：你的动作清单（一页）

> 本文是规范的**宣讲视图**：按"你是谁"重组既有规则，供宣讲与新人上手；规则本体以 `DEVELOPMENT.md`（§4/R10）、`SELF-REVIEW-HOWTO.md`、`PEER-REVIEW-HOWTO.md` 为准，规范修订时同步本文。

## 你是责任人时（每个功能的作者）

**每功能只有 2 次签认 + 过程抽查**（其余全部由 AI 与机器承担）：

| # | 动作 | 要点 |
|---|---|---|
| 1 | 审需求、审测试方案 | 确认意图与验收标准、指挥 AI 迭代——**不签认**（活文档，随时改） |
| 2 | **签认 `design.md`（+ ADR）** | 重点审 R2 上游改动清单——**此签认即 R2 批准落盘**；签认前 AI 不动代码。**仅当 R2 清单变更时须重签**，其他修改不用。新增第三方依赖：另找审批人过目同意，自己代填**文档头部**的"审批人/审批日期"（R11，AI 不得代填） |
| 3 | 过程抽查 | AI 是否越权扩范围（扩了 → 回炉 ②）——**不签认**（test-plan 是活文档） |
| 4 | 双 AI 自审后**签认 `self-review.md`** | 确认换过 AI 评审、主要问题已处置（次要问题可不修，留一行理由）；文档随 PR 提交 |
| 5 | 提 PR | PR 描述 = 交付报告（§7 结构，AI 组装） |

**签认怎么签**：本人编辑文档头部三处——`状态：草案→已确认`、`责任人：<姓名>`、`确认日期`；确认意见可选。**必须本人做，AI 不得代填**（R10）。
**双 AI 规则**：自审必须换一个与主力开发不同的 AI——评审 → 你拍板修/不修 → AI 修 → AI 复审，主要问题清零即通过（不吹毛求疵）。操作照 `SELF-REVIEW-HOWTO.md`，含复制即用的指令模板。
**微改动**（§6 三条件：不碰上游 + 无 ADR + 定制目录内小改动）：免文档管线——双 AI 精简评审（不含 R2 比对）贴 PR 描述、贴验证输出即可。

## 你是评审人时（他人的 PR）

按 `PEER-REVIEW-HOWTO.md` 三动作：

1. **上游接触面 diff 逐行读**（精力与升级摩擦对齐，其余抽查）；
2. **blocker 逐条 confirm/reject，留痕于 PR**；
3. 验证证据抽查（可复跑的抽一条）。

先确认 `self-review.md` 已提交且已签认——缺失即流程违规，request changes。
**建议**换用与作者不同的 AI 跑三项交叉（R2 比对/幻觉验证/缺陷模式扫描）。
**review 是互助，不转移责任**。

## 你随时要守的四条底线

1. 上游文件：未批不动（R2）、动了必带 `AIxCoding` 标记（R3）、批准清单变了必须重签 design；
2. 只改任务必需的内容，不顺手重构（R5）；
3. "测试通过"必须附真实命令与输出（R7）；
4. 以你 git 身份提交的一切都是你的责任（R10 / git 契约）。

## 被抽查时

你的保护与追溯链条：签认字段（谁何时确认）→ `git blame`（谁实际改的）→ PR review 记录——三步对账，责任清晰可查。平时按规则做，抽查就是你的证据。
