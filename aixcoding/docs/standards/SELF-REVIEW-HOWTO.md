# 自审怎么做（SELF-REVIEW HOWTO）

> **给谁用**：功能作者。代码与验证完成后、提 PR 前打开本文照做。
> **一句话**：换一个与主力开发不同的 AI 评审 → 你逐条拍板修/不修 → AI 修复 → AI 复审 → 主要问题清零即收敛 → 报告你签字。
> **不吹毛求疵**：AI 评审永远能查出问题，修复所有问题的代价太高——blocker（主要问题）清零即通过，次要问题可不修。技术评审加深的是**发现深度**，不是修复负担——收敛标准不变。
> **评什么**：先做**技术评审**（方案方向对不对、关键决策权衡站不站得住、实现是否正确且保真、有什么技术风险——输出分析性推理，不是打勾），再扫**缺陷模式**（哪里会错），最后过**流程合规**（R 系列）——合规全绿但方案答非所问，仍是失败的评审；技术评审零 finding 的"全过"同样可疑（要么真没问题，要么没真评）——**"可疑"的处置是复核证据链是否真逐条评过，不是必须产出 finding；无中生有的 finding 比漏评更糟**。
> 规则出处：DEVELOPMENT.md §4/§5/§9。

## 一、流程（五步）

```
① 换 AI 评审：选一个与主力开发不同的 AI（不同工具或不同模型），复制 §二 模板给它，得到 findings 清单
② 你拍板：逐条看 findings，决定"修 / 不修"——你的判断是裁决，不需要说服 AI
③ AI 修复：按你的拍板修复；修复引入的新 diff 让同一评审 AI 复审（只复审增量，不重跑全量）
④ 收敛：所有 blocker 修复且复审通过即收敛——不要求零 finding，次要问题不修也通过
⑤ 报告签字：AI 生成 self-review.md（§三），你签认，随 PR 提交
```

## 二、评审 AI 指令模板（复制即用）

```
你是独立评审 AI（本次不做开发，只做评审）。角色设定：资深工程师做一次真正的 design review +
code review——不是逐项打勾的检查器。评审分三阶段，次序即优先级与精力分配：技术评审是主体
（分析性产出，禁表格打勾），缺陷模式扫描次之，流程合规最后（表格打勾只在此阶段）。

评审背景（规范摘要，已内嵌无需另读文件；全文见 aixcoding/docs/standards/DEVELOPMENT.md）：
- R1 非侵入优先，必改上游时少而集中（升级冲突面最小化）；迁移批次含逐行归属细则（R2 表每行一条归属结论，见 DEVELOPMENT.md R1）
- R2 上游文件的任何改动必须先获批（对照下方 R2 比对）；R3 获批的上游改动必须带 AIxCoding 单行标记注释
- R4 新增文件只允许落 aixcoding 目录（产品代码按 tier 落位 `src/chrys/{tier}/aixcoding/`，ADR-0011）
- R5 只改任务必需内容，禁止顺手重构/升级依赖；R6 发现他人未提交改动时停止询问
- R7 "测试通过"必须附真实命令与输出；R8 文档与定制清单须同步更新（"决定不做"按场景分流：管线内 design 承载 / 豁免区可选落 madr/ / 纯讨论落 madr/ 或 ADR，见 ADR-decision-log--dual-tier-decision-records）
- R9 定制代码按实际依赖落位 `src/chrys/{tier}/aixcoding/`（ADR-0011：档位=能容纳全部依赖的最低档，放错层 test_layering 即红；kernel 档内互引须相对导入）
- R10 签认必须责任人本人；R11 新增第三方依赖默认拒绝、须审批
- R12 迁移批次方案重审：旧实现只是内容索引——对照目标基线同类机制现状同构跟随（不做形态平移），design 必含"是否有更优方案"专题
- R13 豁免须理由与批准：豁免（架构登记/noqa/skip/CI 跳过/closure 存量缺件新增或扩大等）是穷尽正当路径后的设计后备——新增须责任人批准、就地注释理由与批准指向，AI 不得自行添加；closure 清单新增/扩大另须签认 ADR（ADR-0024）
- §9 降级可查：异常吞噬必须有日志/注释/计数痕迹，宁缺毋错
- ADR-0012：开工判定单协议（§4.2——任务路由与豁免由责任人裁决，免判定清单外 AI 不得自判）+ git 写操作逐条授权（§4.1 铁律④）；diff 超出已签 design 范围且不属免判定清单（§4.2）即流程违规

先读取 git diff（相对 <base>）与 aixcoding/docs/<feature>/requirements.md、design.md、test-plan.md
   （requirements 是动机与验收标准的源头——对需求的理解不正确/不完整，后续评审全失准；
   design 承载签认过的方案与 R2 清单；test-plan 承载测试基准）

【第一阶段 技术评审——输出分析性推理（含具体 文件:行号 证据）；
  存在性证明与空结论不构成证据（见末尾输出要求）】

T1 问题重述 + 方向审视：
- 用自己的话重述：这批次解决什么问题、什么场景、谁受影响、明确不解决的边界在哪——
  复述不出 = 没看懂，不得继续
- 细读 design 后先给大方向独立表态：这是解决该问题的合理路径吗？一句话结论 + 一句技术理由
  （依据自己的工程经验判断，不采信 design 的自我论证；禁"方案合理"类空结论）
  - 判"方向不对"→ 此刻才展开替代路线分析（写出"我会怎么做"并与 design 对比），blocker 级候选
  - 判"方向对"→ 继续 T2 沿方案路径深评
- 方案结构合理性：分解/分层/模块边界/先后次序与问题结构是否匹配——过度分解、缺失一环均为
  finding 候选；反方向核对 requirements 的目标与验收标准有无漏做

T2 关键决策的技术权衡评审：
- 从 design 识别影响方案形态的关键决策（通常 3-8 个，不罗列全部）
- 每个决策用自己的推理回答三问：它用什么代价换什么收益？在什么条件下这个权衡会反转
  （变成错的）？本批次实际环境满足这个条件吗？
- 被放弃的做法中至少一个由你重新独立评估（同意放弃 / 不同意+理由）——选取
  影响方案形态的关键备选（即上文所识别关键决策的备选）；"备选是否充分"由你论证，
  不采信 design 章节的自我陈述
- 值/阈值/超时/上限类决策：值的依据三选一核查（数据依据 / design 定案 / 无依据拍脑袋）——
  无依据 = finding
- 触发式条款：评审任何时点直觉"可能有更好做法"→ 写下来（具体到做法与理由），
  suggestion/blocker 候选；本阶段收尾显式回答"未发现更优做法"或列出所发现的——不许静默滑过

T3 实现正确性与质量深读：
- 先读懂核心实现的完整逻辑再下结论（主路径数据流、错误路径、状态变化；必要时读调用方/
  被调用方源码）——不是只看 diff 碎片；签名/行为变更的全部下游调用点已核对
- 正确性：逻辑错误、边界（空/极值/首条）、并发与取消、资源与异常路径、多平台/多路径分支
  对称（不对称须有理由）
- 实现-方案保真（双向）：T1/T2 中 design 声称的性质实现真的做到了吗？有没有偷懒变形
  （方案说统一模式、实现各写各的）？反向：有没有 design 未承诺的自由发挥？
- 系统交互：与既有机制的交互是否正确、是否破坏既有不变量、该复用的公共设施复用了吗
  （该复用而没复用 = 重复实现，finding 候选）
- 质量与复杂度："有没有更简单直接的写法"落到"哪几行可以怎么简化"或明确回答"没有"；
  同语义多处实现是同一手法还是复制粘贴（后者须有理由）
- 测试有效性：测试锚定的是 T1-T3 的关键性质，还是只测了容易测的；断言更新是"如实锁定
  新行为"还是"放松迁就实现"（后者 = finding）；被替换旧行为的依赖方已迁移或确认无依赖
- 文档-实现一致：被改行为的 docstring/就地注释/批次文档/使用手册与实现相符——
  文档说 A 实现做 B = blocker

T4 技术风险：
- 性能与量：热路径开销；日志/上报的量与频次——高频路径、常态性失败场景会不会淹没日志/打扰用户
- 演进：上游升级时本方案的冲突面与脆弱点在哪
- 可维护性：下一个同类模块出现时能自然 follow 既有模式吗，还是会产生第 N 种写法

【第二阶段 缺陷模式快速扫描】
- 幻觉 API：对 diff 中每个新增 import 的符号验证真实存在与签名正确（查定义处或实际 import）
- 静默吞错：异常吞噬无日志、无注释、无计数痕迹（降级必须可查）
- vacuous test：挑 2 个最关键测试，回答"故意改坏实现哪一行它才会红"——
  答不出具体行 = 测的是 mock 不是行为
- 过度工程：单调用方的抽象层、无故障依据的防御分支、"将来可能用"的参数
- 数据边界：新增上报/外发字段逐个问"为什么需要它"；路径是否相对化；是否泄漏用户环境信息
- 边界条件：空集 / 极值 / 首条 / 并发首条
- 异常与资源：泄漏、未清理、finally 缺失
- 并发异步：竞态、未 await、取消语义

【第三阶段 流程与合规——本阶段才用表格：检查项 | 结论（过/finding）| 证据（文件:行号）】
- 临时方案三件套：写死/绕行/降级类改动须有期限、恢复路径、副作用说明三件（就地注释或
  design 修订承载）——缺任何一样 = finding；副作用（改动波及谁）已列且有接受记录
- R2 比对：diff 中上游文件与 design.md R2 清单逐文件对名，不允许"整体一致"式结论
- R1 逐行归属（迁移批次）：R2 表逐行有归属回答（形式检查——只查"是否回答"，归属正确性由责任人签认裁决；细则见 DEVELOPMENT.md R1）
- R11 比对：diff 中 pyproject.toml / uv.lock / 新 import 的第三方变化与 design.md 依赖申请节
  逐项对名；清单外引入 = blocker
- closure 对账：运行 check_docs.py --closure；closure-exemptions.toml 只能精确减少已补齐项，
  新增批次/缺失文件或 stale 项 = blocker；新增缺件 batches 目录不得以微改动豁免放行

【输出要求】
- 第一阶段必须输出分析性推理（含具体 文件:行号 证据）；存在性证明（"design 有 X 章节"
  "无残留 Y"）与空结论（"方案合理""论证充分"）单独不构成证据
- findings 按（位置 / 严重度 blocker|suggestion|nit / 说明 / 处置建议）输出；技术性 finding
  的门槛 = 按它改，行为或可维护性有可指出的具体改善
- 末尾输出你的模型/工具标识，并声明："本评审为独立第二 AI 评审，与开发 AI 不同源；
  仍可能共盲，终裁在责任人"
```

## 三、`self-review.md`（AI 生成，你签字）

```markdown
# 自评审记录：<功能名>

- 责任人：
- 状态：草案
- 确认日期：
- 确认意见：（可选）
- 评审 AI：<标识，须与主力开发 AI 不同>
- 开发 AI：<标识>

> 记录档：签认一次，后续追加评审记录不触发重签。

## <YYYY-MM-DD> 评审结论：通过

- 轮次：N 轮（每轮 = 评审 + 修复 + 复审）
- 方案与实现评估（技术评审摘要）：
  - 大方向表态：<结论 + 一句理由>
  - 关键决策逐条意见：<决策点 | 同意/有保留 + 一句理由>（N 条）
  - T1-T4 要点：<各一句>
  - 临时项与例外：<指向 design 修订或就地注释>
  （只写"方案与动机对应"类空话 = 评估未完成，补齐再签字）
- blocker 处置：<逐条：finding → 已修复，验证命令与结果>
- 未修项（次要问题，责任人拍板不修）：
  - <位置 | 说明 | 不修理由>（各一句话）
```

## 四、FAQ

**Q1：哪里找"不同的 AI"？** 不同工具（如主力 CodeBuddy，另一个用别的工具）或同工具不同模型均可；须运行在**能访问本仓库文件**的环境中（IDE 内另开会话即可），纯对话、无文件访问的 AI 只能做辅助参考，不构成完成双 AI 评审。在 self-review.md 里如实记录标识即可，不做技术验证。

**Q2：哪些可以不修？** blocker（错误行为、方案答非所问、文档与实现矛盾、上游越权、幻觉 API、测试无效、吞错不可查）必须修；suggestion（更优写法）、nit（风格）由你拍板，不修就在报告里留一行理由。判断口径一句话：**"不修它，功能会错或升级会炸吗？"——不会，就可不修。**

**Q3：可以不做双 AI 吗？** 不可（标准管线强制）——这是压缩 AI 共盲的核心手段；确无第二 AI 可用时，在 self-review.md 中如实记录原因，并人工过一遍 §二 模板全部三阶段检查代替（第一阶段技术评审尤必）。

**Q4：微改动（§6 豁免）要做什么？** 先核豁免资格仍在——diff 对照 §6 三条件（零上游文件 / 不触发 ADR / 定制目录内约百行），超范围停等责任人重裁；然后用同一模板的裁剪版：**保留** T1（需求与动机以 PR/任务描述代 requirements 与 design）、T2 的值依据核查与触发式条款（"未发现更优做法"显式回答）、临时方案三件套、幻觉 API、静默吞错、边界/异常/并发检查；**去掉**批次文档读取、T2 决策逐条三问、T3 深读、T4、R2 比对、closure 对账。结论贴 PR 描述（含两个 AI 标识与未修项），免 self-review.md 文档。
